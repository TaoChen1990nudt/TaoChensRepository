# 2026-11-01

## Phase 101 — 让断言真的能看见东西

这一轮**没有新功能**。它补的是 P99 与 P100 各留下来的那一条存活咬测，而两条的根子
是同一个：**插入链是空的**。

### 起点：P99 第 (7) 段的注释自己把答案写出来了

翻回 P99 加的推子前那条断言，它的注释第一句是：

> With no plugins in the session the two taps carry the same signal, so
> "still exactly twice" is what says the OTHER line was bought, pushed and read.

「无插件时两条抽头拿同一份信号」——这句话当时被当成**前提**写进了注释，而它其实是
**盲区的定义**：如果两条抽头拿的是同一份样本，那么「push 在插入之前还是之后」在样本层面
是一个**恒等变换**。所以咬测 M6 在 P99（1008 条）与 P100（1024 条）两轮都全绿，看起来
像「无头会话测不到真插件的行为」。

**它测不到不是因为无头，是因为链里什么都没有。** 只要链里有个东西会改信号，
插入前后就是两份不同的样本，位置写错当场红。

### 修法：不用新效果，挂一个 `drive`

```
mx.setInsertType (0, 0, fx::Type::drive);
mx.setInsertEnabled (0, 0, true);
```

选 `drive` 而不是 `lowPass` / `eq` 的理由是**它无状态**——`applyDrive` 里那句
`juce::ignoreUnused (state)`。夹具里 `renderOnce()` 会被调三到四次，而 `ChainState` 在
引擎里是持久的：一个滤波器会把上一轮的尾巴带进下一轮，两次渲染就为一件与抽头无关的事
而不同。这种「为错误的原因而不同」最麻烦，它会让人以为夹具坏了。

### 第一次修，判据方向反了

推子前那条仍然用 `doubled == 2 × single`。它红了（-2.9 dB），但**代码是对的**：

- `single` = 直连，**经过 DRIVE**；
- `doubled` = driven 直连 + **干的** pre 副本。

要求 `doubled = 2 × single`，等于要求 pre 副本**是 driven 的**——那恰恰是「抽头在插入
**之后**」的定义。**判据在测反面**，而且反得非常隐蔽：它红的时候看起来像实现错了。

正确期望是 `single + dry`，而 dry **必须量出来**——旁路 DRIVE、撤掉 send、再渲染一次。
于是 `measure()` 从固定的 `2 × single` 改成接受一个**期望 buffer**：

```cpp
const auto measure = [&] (const juce::AudioBuffer<float>& other,
                          const juce::AudioBuffer<float>& expected)
```

三条渲染各自有各自的期望：`single`（driven）、`dryOnly`（dry）、`preDoubled`
（driven + dry）。改完之后两条都是 **-180 dB**。

一般规律写进了 PITFALLS P101-B：**非线性处理的测试不能用「输入 × 常数」当期望值**，
那个等式只对线性链成立。夹具里每加一个非线性插入，所有用比例做期望的断言都要重看一遍。

### 第三条：断言的前提本身要写成断言

补完 `drive` 之后出现了新的退化路径。**如果 DRIVE 根本没生效**（类型写错、没 enabled、
链没跑），`single` 就等于 `dryOnly`，于是 (7) 的期望 `single + dry` 变成 `single + single`
= `2 × single`，正好等于 (6) 的期望——**两条断言合成一条，而且都绿**。

这不是假想：咬测 M7（把类型改成 `none`）正是这个结果，精确红 1 条，而红的是新加的那条。
所以加了第三条：

```
[PASS] DRIVE 真的改了信号（否则两条抽头断言会退化成同一条）   (0.6022)
```

它不检查被测行为，它检查**被测行为还有没有意义**。写它的信号是：发现自己要说「这条断言
在 X 成立时才有效」——那就把 X 也写成一条断言。

### 咬测三项全红

| | 变异 | 结果 |
|---|---|---|
| M6 | `pdcPre` 的 push 挪到插入**之后** | 红 1（`-5.1 dB`，正常 -180） |
| M6b | post 抽头改读 pre 线 | 红 1（`-6.0 dB`） |
| M7 | 插入类型改成 `none` | 红 1（只有前提断言，精确） |

M6 是 P99/P100 两轮都存活的那一条。它现在红了——**没有任何新代码，只改了夹具**。

### 顺带把 P100-D 的结论改对

P100 记的是「键的读取时刻同样咬不住，与推子前抽头同一个根，要有一个能自己报延迟的
测试用插入」。做完这一轮才看清结论**不是那个**：

`solve` 的键边 `offset = own[source]` 保证了 `entry[L] >= entry[S] + own[S]`，所以

    delay = entry[L] - (entry[S] + own[S])  >= 0，且在最简单的拓扑里**恒等于 0**

`jmax(0, …)` 之后那一步 `readInto(target, 0)` 是**正确的**，把它硬写成 0 是无害的。
这不是「测不到」，是**那段代码在单层拓扑下不可达**——它只在听者还被另一条更慢的支路
推后时才非零。

于是给自己立了一条区分（PITFALLS P101-C）：

- **「测试没覆盖到」**——加断言就能变红（P101-A 就是这一类）；
- **「代码路径不可达」**——加断言**也不该**变红，因为它在当前设计下永远走不到。

判据是问：**这个分支要成立，需要什么前提？那个前提在当前拓扑里会发生吗？**
如果答案是「需要听者还有一条更慢的支路」，就把它记成不变量，而不是记成待补的盲区——
否则下一轮会去硬造一个 104 采样错位的脆弱测试，那是在测自己的算术。

# Phase 102 — 第一个真的会迟到的内置效果

## 为什么做这个

昨天（同在 11-01）P101 补完了 P99/P100 的存活咬测，那一轮的结论是「断言的第一步是让被测对象
真的被改变」。今天拿同一把尺子量 PDC 自己，发现它从 P83 起就一直在验**表**：

- P83 建了 `pdc::solve` 与延迟线；
- P99 把边从 bool 升级成 `edgeLatency(from,to,offset)`；
- P100 加了第四种边（侧链键）；
- P101 让抽头的位置看得见。

四轮都改对了，但**没有一次有声音真的迟到**。原因很直白：每个内置效果按构造都是零延迟，
唯一能让一条通道晚下来的办法是 `setInsertLatencyForTest` —— 那是测试自己打的一个数，
验证的是 P83 的算术对 P83 的算术。所以这一轮做了一个**按构造就该晚**的插入：
`fx::Type::limit`，前视限幅器，信号走 128 采样的延迟线，探测器读还没延迟的那个样本。

## 三个决定

**① 延迟是插件的属性，不是旋钮。** `fx::lookaheadSamples = 128` 是常量，
`fx::builtInLatency(Type)` 是引擎唯一的问题，`publishSchedule` 逐个插槽求和。
做成旋钮的话，一个旋钮会在音频流过去的时候改图的拓扑——那是另一件事，不是「加个参数」。
顺带把 P83 那句「只有托管 VST3 会迟到」的注释改成事实：它在这条插入面前是假的。

**② 启动时间不是一个参数。** 它就是那 128 采样宽（四个时间常数，98% 的衰减在峰值到达时已经
到位）。比它短会跳，比它长等于没有前视。压缩比是无穷，所以天花板是精确的：
1.5 的峰值穿 -20 dB 出来是 0.1023。增益乘在**延迟之后读出来的**样本上。

**③ 主输出上的晚插入不需要补偿。** 整首一起晚，`maxPdcLatency` 仍然是 0。
这不是特例，是 `finishedDelayTo()` 的自然结果，自检第 7 条把它钉住了。

## 被咬的四次

**M1（`builtInLatency` 返回 0）** 红 3 条：规则、表（0 → 0 → 0）、对齐 -1.1 dB。
**M2（读当前槽而不是 128 之前）** 红 4 条。这一条第一次是**存活**的 —— 见下面第四点。
**M3'（先压再延迟）** 精确红 **1** 条。延迟、天花板、峰值、表、对齐全对，少的只是前视。
**M4（汇合点不等待）** 红 2 条：P83 的老断言 + 这一轮的对齐 -1.1 dB。

## 咬到的四件事

**A. 空日志 + 秒退 127 是帧太大，不是代码错。** 第一次跑出来 0 字节日志、退出码 127。
`ATOMIC_TRACE=1` 一行都不打 → `runSelfTest()` 在进门就死了。CMakeLists 里 P25 的注释早就写着
这件事（8 MB → 64 MB，原因同样是「`[&]{}()` 会被内联，不给新帧」）。六个夹具把它推过 64 MB，
于是 128 MB。**以后认这个症状：空日志 + 秒退 = 栈，全绿全红才是代码。**

**B. 参照要量在「被测对象不存在」的图里。** 第一版的对齐断言拿「同一张图里单独渲染的那条」
当参照，它**永远绿**：控制台把每条路都等到最慢的那条（连没声音的条子上的插入也算数），
所以参照自己已经晚 128 了。诊断打出 `bestShift 128, residual 0` 才看清。
改成两份参照都用**没有那条插入的 `MixerModel`** 之后，M2 立刻红 -4.4 dB。
判据一句话：**被测的东西坏掉时，这条断言的期望值会不会跟着一起坏？**

**C. 只体现在「时间顺序」上的错误，幅度断言测不到。** 先压再延迟的实现，七条里六条绿。
唯一能分辨的是「衰减比峰值早到 128」：正确实现里那段安静尾巴 0.0499 → 0.0065，错法里纹丝不动。

**D. 块可以长，环不能。** `applyLimit` 第一版把块长截在容量上，引擎里 512 采样永远够，
但夹具给了 8192，于是最后 128 个样本原样漏出去。改成切块。
