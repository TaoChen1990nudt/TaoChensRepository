## Phase 96 — comping：从几遍里拼出一遍

诊断第 2 条的后半。P95 让一组 take 只有一遍出声，但「这一遍的第 1–4 小节好，第 5–8 小节要另
一遍的」还是做不到：只能整遍选。这一轮把拼接做实，接缝 4 ms 交叉淡化，拼出来**仍然是一个组**。

**判据与数字**：`Source/Model/Comp.h`（`namespace comping`）是纯规则 —— `crossfadeSeconds =
0.004`、`minRangeBeats = 0.25`、`fadeBeats(secondsPerBeat)`、`fadeFraction`（按块的**自身长度**
折算，钳在 0.25）、`noteJoins`（只认起点在区间内的音符）、`blockJoins`（块碰到就算）、
`addEdgeFade`（在原曲线上乘，不另画一条）。

**为什么是「替换这个区间」而不是「记住哪一遍从哪到哪」**：后者要一份分段表活过存盘，而 P95 的
集合是**派生的**，没有实体可以挂它。写成「把这段换成那一遍的材料」之后，三处接缝就是三次
独立的编辑，顺序无关、重复无害，也不需要任何 provenance。

**第一次拼接先分一份**：`NoteGroup` 加 `comp` 标记（v31 的 `takecomp`），拼接目标是 set 里
**第一个带标记的组**；没有就先从「当前那一遍」复制一份新的 take（序号 = 集合里最大 +1）并把
它设为当前。所以「用第 1 遍接第 10–12 拍」不会动第 1 遍，而第二处接缝改的是同一份 comp，
不会又分一份。名字后缀 ` 拼接` —— 这是「这一遍是拼的」唯一可见的记号。

**接缝**：进来那一段比接缝早 `fadeBeats` 开始、比结尾晚 `fadeBeats` 结束，两侧邻居各在自己
那一端淡到 0，于是四毫秒里两遍同时在场、增益互补。少掉那个提前量就退化成「淡出 + 淡入」，
中间是一段静音 —— 那不是交叉淡化。

**切块复用刀**：`PianoRollComponent::splitSampleBlocksRaw` 是从 `splitSamplesAt` 里拆出来的
算术半边（不动选区、不发通知、不重画）。P50 那套源窗口 / 变速 / 倒放的换算一行没重写，
拼接过程最多切四次，全是中间步骤。

**手势**：编组栏 take 菜单里多一项「用这一遍接上 1.0 - 3.0 拍」，区间取**循环区间**（不看开关，
`LoopRegion::hasSpan()` 就是问这个）。它已经是全应用唯一一对可以拖着设的拍，再让用户画一遍
是让他把同一件事做两次。

**存盘**：v31，只多 `<Group takecomp="1">`，且只在「是 take 且是 comp」时写 —— 没拼过的工程
与 v30 逐字节相同。读侧要求 `takeset > 0` 才认标记（普通组不可能是拼出来的）。

自检 933 → **953**。咬测 3/3：把 `fade` 改成 0 → 4 条接缝断言红；去掉肩点 → 5 条红（连渲染
电平都塌）；每次都新分一份 → 1 条红。

**这一轮最值得记的一件事**：原本打算用「渲染里接缝处的最大跳变」当判据，**咬测证明它咬不动**
—— 采样器在块边沿本来就有一小段包络，把 fade 改成 0，最大跳变只从 0.00040 变成 0.00046。
真正的证据在**块自己**：提前量 + 三块贴在接缝那一端的曲线值是 0。原来那两条渲染断言因此删掉，
换成 4 条模型断言。

被切成三段的块 —— 4 ms 的接缝在任何缩放下都是同一条边。菜单项 headless 拍不到。与 P95 逐
字节比 25 同 / 8 异，8 张全部来自抖动集（同一份二进制跑两遍，同样这 8 张不同）。

## Phase 97 — 力度：一根柱子一个矩形，一次拖动一个 delta

诊断第 3 条（4×4÷3）的前半。力度在此之前只是钢琴窗右下角的一个读数（`vel 0.80`），没有任何
编辑手势 —— 一条 16 个音符的乐句要把重音改下来，只能逐个别点开内联框。这一轮给它一条 lane。

**数值规则**：`Source/Model/VelocityLane.h`（`namespace velocitylane`，header-only）—— `clamp`
的地板是 `0.02`、`shifted(from, delta)`、`fromY/toY` 是**线性**映射（`box` 顶 = 1、底 = floor）。
三个决定写成注释留在文件里：

1. **线性轴**，不是 dB、也不是 MIDI 的平方律。听感的高端全挤在 0.9–1.0，曲线轴会把半屏分给
   听不出差别的地方。
2. **地板 0.02 不是 0**：0 在音乐里等于"没有这个音"，那是静音与删除的语义。
3. **拖动记 delta 不记绝对值**：否则「框选一排再拖一下」会把一排全设成指针下那个数，
   第一个像素就把重音削平。

**几何只有一个**：`velocityBarFor (note)` —— `right = jmax(head + 3px, jmin(tail, head + 16px))`、
`top = toY(velocity)`、`height = jmax(2px, …)`。paint、`velocityBarAt`、`hitsInMarquee` 都问它，
所以"画出来的 == 抓得到的 == 框得到的"不是三处实现对齐，是一处实现被问三次。空手按下是 lane
内框选，`marqueeInLane` 一旦为真，`hitsInMarquee` 只收柱子并直接返回 —— 带子不该抓到网格里的块。

**没有新数据通路**：改的是 `NoteEvent::velocity`，通知走 `notesChanged()`，撤销靠鼠标手势的
`beginUndoGesture/endUndoGesture`，编组靠 `expandToWholeOccurrences`。所以 `formatVersion` 不动
（仍 31），`[PASS] 改过的力度存得下、读得回` 这一条就是它的论证。

**新增文件两个**：`Model/VelocityLane.h`（69 行）与 `UI/PianoRollVelocity.cpp`（401 行，第十三个
TU）。工具栏第 10 个按钮「力度」开合 lane；顺手把吸附按钮拿回磁铁 —— 它原来借的是**解组的图标**
（`drawToolIcon (g, 7, …)`），磁铁那个分支是死代码。

**还补了一个欠了十条街的入口**：`setTopPitch / getTopPitch`。滚动的两条轴以前只有横向能从外面
定位（`setScrollBeats`），所以"保证某个音高在画面里"只能靠猜 —— `-velocity` 第一版就这样拍出

## Phase 98 — CC：一条通路，一个纯函数

用户说「按你的想法进行」，按复盘排的优先级开工，第一条是 CC lane（诊断第 3 条后半：
力度能改、CC 不能，那是半个功能）。

**开工第一件事是推翻上一轮自己的结论。** `STATUS.md` 里写着「CC 曲线在模型里已经有了
（`Take::controls` → `NoteGroup` 的 lane）」——`Take::controls` 这个类型**根本不存在**，
`grep -rn "ControlPoint\|ControlLane" Source/` 零命中；更关键的是 `Source/Audio/` 里除实时
输入**没有任何 `MidiBuffer` 生产者**。也就是说 PC 键盘之外，宿主音源从来没收到过一个控制器
事件。所以这一轮真正的工作量在**数据通路**，不在画图。判据写进 MEMORY 第 31 条：
**「我上次写的」不是证据，源码是。**

**三条决定：**

1. **复用而不是新建。** CC 就是「绝对拍的 0..1 折线」，跟内部参数自动化是同一个东西，
   所以 `Model/MidiCc.h` 里三条常驻 lane 直接装 `AutomationLane`。没有第二种插值、
   没有第二个 `addPoint`。
2. **去重放进纯函数。** MIDI 控制器是**状态**不是事件——一条平线如果每块都发，几百条
   消息。`midicc::valueToSend (points, enabled, beat, lastValue)` 做三件事：lane 没开不发、
   值跟上次一样不发、其余返回 `0..127`。抽成纯函数的好处是**这条规则在无声卡的 headless
   自检里能咬**——音频线程那侧只剩下「调它、有返回值就 `addEvent`」。
3. **哨兵是 -1 不是 0。** 0 是真实控制器值（无调制）。这个决定后来救了一次咬测，见下。

**忘记记忆值**：`lastCcValue` 是每个插槽每个 lane 的"上次发过什么"。跳到别处再回来还带着
上一段的值就会漏发第一条。用 `ccEpoch`（`setPositionBeats` 里 `fetch_add`）让音频线程每块
比一次，变了就全填 `nothingSent`。`resetMixState` 里也清。

**面板**：一条 strip 四个页签（力度 / CC1 / CC11 / CC64），不叠四条 lane——叠四条要重新
算 `laneTrackArea` 的分配，而四页签只是换个 `laneTab`。`ccPointFor` 是唯一几何，画、命中、
测试都问它。**点一下曲线就把 `enabled` 打开**：「画了没反应、开关在三级菜单外」是最贵的
困惑。左上角 HUD 在有插件音源时写「→ 已连到宿主音源」，走内置振荡器时写「→ 内置音源，
收不到 CC」——判据是 `routing::layerSlotId` + `pluginId`，与 `publishSchedule` 同一份。

**自检 969 → 988。** 四段夹具：页签几何（`getLaneTabBounds` 四行等高不重叠）、点与拖
（`simulateCcClickForTest` 建点、拖拽跟手）、存盘往返（`<CC number="1">`，数出现次数而不是
查某一个）、发布到 slot（有插件 → `slotId >= 0`，无插件 → `-1`）。另有纯函数段验证发送规则。

## Phase 99 — 发送与返回：一条信号走两条路，还在同一刻到

先读诊断原文（`docs/review-p92/scorecard-report.md` 第 109 / 118 行）。验收原文是
「**反相测试：同一信号经『通道直连主输出』与『经一条 send 到 return 再回主输出』，残余 ≤ -60 dBFS**」，
动作原文是「通道加 **2 条 send**（**推子前/后可选**）+ **独立 return 通道**；COMP 加外部键输入…
**侧链延迟并入既有 `pdc::solve` 的唯一延迟表，不要新开补偿路径**」。这一轮做前两项，侧链没动。

**「独立 return 通道」不需要新概念。** send 落地的那条通道**就是** return，判据是
`isSendTarget(channel)`——它没有自己的声部，`busUsed[]` 由 send 置真。加一个 `ReturnChannel`
类型会立刻引出「return 能不能有 send」「能不能被删」这一串问题，而答案全都是"和普通通道一样"。

**模型**（`Model/MixerModel.h`）：`Send { destination, levelDb, preInsert, enabled }`，
`noSendDestination = -1`（**不是 master**），`isLive()` = 开着且有目的地，`-48 dB` **就是零增益**。
`wouldLoop` 从"单游标走链"改成 BFS——send 一进来，一个出口的假设就不成立了，而它失败的表现是
**环里的通道永不 ready、整段静音，UI 上一切正常**。`setSendDestination` 先把旧边临时清空再问
「这条新边成不成环」，否则"把 send 从 1 改成 1"会被自己挡回来。`sanitiseOutputs` 改名
`sanitiseRouting`：悬空的 send **直接关掉不重定向**（没有一条"明显该指"的路）。

**引擎**（`Audio/PlaybackEngine.cpp`）三处：
1. `publishSchedule` 把 send 解析成 `ScheduledSend { destination, gain, preInsert }`；
2. **拓扑即算术**：一个 `edgeLatency(source, destination, offset)` lambda 同时回答排序与延迟表
   —— post 边 `own[from]`，pre 边 `0`。`pdc::solve` 的接口因此从 `feeds(from,to)->bool` 升级成
   `edgeLatency(from,to,int&)`，Phase 83 的薄封装留在原地，老断言一行没改；
3. 渲染：推子前抽头用**第三条延迟线 `pdcPre`**（插入是就地改写 bus 的，「稍后读」拿到的是
   处理后的信号），`pdcExit` **一块只 push 一次、多处读**，`Line::readInto` 加了 `gain` 参数
   （send 电平不必再借临时缓冲）。

**面板**：每条通道两行 send（行高 14，`getSendRowBounds`），**两行常驻**——一行只在接上时才出现，
会让通道条高度在鼠标底下变。`getFaderRowBounds` 顶部多减 `2*14`，推子与电平表从**同一个**行矩形
派生，所以一起下移 28 px、一起变矮。文字 `→ 6  -6.0` / `→ 7  -12.0 p` / `—`。

**存盘 v33**：`<Send index to db pre>`，只写活着的；读侧**先 `setSendDestination` 再电平/pre/开关**
（没目的地打不开）。`carriesState()` 加两条：自己是 target 或有活着的 send。

## Phase 100 — 侧链键：一个键就是「喂探测器的发送」

诊断最后一条的后半，也是那五条诊断的收口。开工前先读了一遍 `Effects.h`：**内置 COMP 是有的**
（`fx::Type::comp`，六参数，linked-stereo 包络），所以这一轮不用新写 DSP，只需要给它的
探测器换一个输入，并把「换谁的」这件事接进既有的图与延迟表。

**一个概念就够了。** 键 = 一条发送，落点不是总线而是压缩器的探测器。于是：
同一个 `reaches`、同一张 `edgeLatency` 表、同一个抽头位置（源的**成品**信号 = post-insert）。
不需要 `ScheduledKey` 这个新结构，也不需要第四条延迟线。

**四处判断（都写进了注释）：**
1. **存在听者身上**：`MixerModel::channelKeys[listener] = donor`。谁需要信号谁声明依赖。
   副作用是这条边**从源指向听者**，而 `reaches` 原本只会从「我」往外走（`out`/`send` 都存在源身上）。
   所以 BFS 里多扫一遍「谁在听我」。这是「链变图」之后的第二个落点，漏了它
   `0→3→4→0`（其中一条是键）就查不出来 —— 咬测 M3 只红这一条。
2. **`noKeySource` 是 -1 不是 0**：0 是 1 号通道。`std::array<int>` 默认全零 ⇒ 出厂工程
   每条通道的压缩器都听 0 号的声音。构造函数 / `resetToDefault` / 读盘暂存各 `fill` 一次。
   （PITFALLS P100-B；同一个坑这个项目已经踩过三次。）
3. **模型查环比发布严**：模型不看插入类型（宁可多拒一条"将来加了 COMP 才成环"的接线），
   发布只把「真的有一个活着的 COMP 在听」的键算成边。否则一条空接线会把整条通道拖慢
   96 采样，而没有任何声音上的理由。`[PASS] 没有压缩器在听的时候，键不发布成一条边` 就是它。
   咬测 M7（去掉这层过滤）红的那一条。
4. **面板只给一个 `K5`**：中文「键5」在 8 px 下糊成一团，而这一格另外四个词
   （COMP / EQ / THR / DRIVE）都是 ASCII。设置入口在插槽的右键菜单里（子菜单「侧链键」，
   成环的源灰掉）。标记跟着**通道**走，所以同一条通道上两个 COMP 印同一个 `K5`。

**DSP 只在一处分叉**：`applyComp` 的 `level` 从 `fx::KeySignal` 来还是从 buffer 来，
增益计算 / knee / attack / release / makeup 全部共用一份。`KeySignal::left == nullptr`
（没接）与「接了一条静音的线」是两件不同的事 —— 前者听自己，后者把包络放下来。写进注释了，
免得下一个人"顺手合并"。

**引擎的读法**：`channelKeyBuffers[listener]`（只为有键的通道分配），在**听者**这一轮、
插入**之前**读，`delay = entry[听者] - (entry[源] + own[源])` —— 与 `finishedDelayTo()` 是
同一个减法，因为它是同一个抽头。行没准备好且 `delay > 0` 时**不交键**（不交静音），
而**不是** `continue`：第一版写成了 `continue`，那会把整条通道静音，是「缺一个探测信号」
被做成了「静音一条通道」。

**验收两条（一条管探测器，一条管通路）：**
- DSP 级：-46 dBFS 的安静信号在 -30 dB 门槛之下，本来一个采样都不该动（`0.005000` 进 `0.005000` 出）；
  接上 0.9 的键之后末样掉到 **`0.000208`**（-27.6 dB）。
- 渲染级：把键换成一条**静音**的通道 —— 压缩器不再自压，rms 从 `0.02195` 涨到 **`0.10243`**（+13.4 dB）。
  这个方向是故意的：如果键没送到，两次渲染**逐样本相同**，断言当场红。

**咬测 9 项：8 中，1 存活（盲区）。**

| | 变异 | 结果 |
|---|---|---|
| M1 | 键边的 `offset` 记成 0 | 红 1（`entry 0 total 96`） |
| M2 | `setSidechainSource` 不查环 | 红 1 |
| M3 | `reaches` 不走键边 | 红 1（隔一条键的远环） |
| M4 | `applyComp` 忽略键 | 红 2（DSP + 渲染） |
| M5 | 引擎不把键交给链路 | 红 1（只红渲染级 → 与 M4 分工清楚） |
| M6 | 删通道不重编号键 | 红 1（`s0 1 s4 6 s5 -1`） |
| M7 | 不按「有 COMP 在听」过滤 | 红 1 |
| M8 | 读盘但不提交键 | 红 1 |
| **M9** | **键按 `delay = 0` 读** | **1024 全绿** |

M9 与 P99 的 M6 是**同一个根**：无头会话里没有 VST3 ⇒ `own` 恒为 0 ⇒ `delay` 恒为 0。
表那一半已经咬住了（M1），缺的是「渲染器真的按表读」这一半。要补，得先有一个能自己报
延迟的测试用插入 —— 已经记进 STATUS 的"下一步"。

**两次返工，都是快照：**
- 第一版让 1 号条听 3 号条，画面里两行都是干干净净的 `COMP`。不是标记没画，是
  `setSidechainSource(0, 2)` **被模型正确拒绝了**：演示控制台在快照前被
  `showDemoConsoleRouting()` 摆成 `1 → 2 → 3 → 主输出`，3 号是这条通道的下游。
  夹具没看返回值，于是一个正确的拒绝长得跟一个坏掉的功能一模一样（PITFALLS P100-C）。
- 第二版改成两行都挂 COMP，结果两行都印 `K5` —— 键属于**通道的探测总线**，不属于某个插槽。
  于是第二行换成 EQ：`COMP K5` 与 `EQ`（无标记）并排，才说得清这个标记是什么。

**快照 37 帧**（新帧 `-sidechain`）。与 P99 逐字节比 **24 同 / 12 异，12 张全在抖动集**
（这一轮没有一张真改动：P100 没画任何既有帧，`K5` 只在接了键时出现，而演示工程没接）。
`-sends` 与 P99 逐字节相同，是「没碰发送」的旁证。`-clipauto` 仍与 P98 差那一个抗锯齿像素、
但与 P99 逐字节相同 —— 换了三个 TU 的代码它却没再动，说明 P99 那条「AA 取整平局」的结论站得住。
`-sidechain` 自己的确定性只在右半（x > 1150 的效果器架）；左半与所有混音台帧一样落进抖动集
（那是电平表）。
