# P122 — 插件窗口的外框和音源实际界面只认一套尺寸

用户报的是双屏下的错位：加载了外部音源，调整音源界面大小时有时界面不会跟着缩放；
音源界面一开始在一个屏里显示得很大，移到另一个屏里变小之后，音源的边框与音源实际界面
之间有一段黑色的距离，而且拖外框时实际界面不跟着变；但直接拖音源自己的右下角调整三角
是可以改大小的。

## 诊断

最后半句是钥匙：编辑器自己改走得通（`setContentOwned(editor, true)` 的 `childBoundsChanged`
一路本来就是通的），宿主 → 编辑器那一路走不通。

查 JUCE 8 源码：

- `VST3PluginWindow` 是宿主塞进 `DocumentWindow` 的编辑器，自己的 constrainer 由插件的
  `checkSizeConstraint` 说了算；换显示器时 `nativeScaleFactor` 跟着变，编辑器重算出来的
  合法尺寸也跟着变。
- 我们构造窗口时硬写了 `setResizeLimits(…, 2600, 1600)`。**`setResizeLimits` 会替换窗口的
  constrainer**，于是变成第二套尺寸：外框允许的大小插件不认。插件一拒绝，露出来的就是
  VST3 `ViewComponent` 里那块 `Colours::black` 的 `Inner` —— 用户看到的黑边。

## 改法（照 JUCE 自己的 AudioPluginHost）

1. 窗口的 constrainer 换成 `EditorConstrainer : BorderedComponentBoundsConstrainer`：
   `getWrappedConstrainer()` 交回编辑器自己的那一个，`getAdditionalBorder()` 扣掉原生边框与
   `getContentComponentBorder()`。删掉硬编码的 `setResizeLimits`。没有编辑器的插件仍走普通分支。
2. `getDesktopScaleFactor()` 钉在 `frameDesktopScale = 1.0f`：原生视图自己管 content scale，
   宿主再乘一层就是两层缩放。
3. 构造参数从 `AudioPluginInstance&` 放宽成 `AudioProcessor&`：窗口只用 `createEditorIfNeeded()`，
   headless 那个 Test Synth 没有编辑器，自检改用合成编辑器才咬得住上面两条。

## 自检 1167 → 1173（+6）

DPI 钉死 / 编辑器自己改外框跟着 / 外框改界面铺满不留黑边 / 约束器委派 / 上限确实夹住 /
没有界面的插件仍有一扇窗且不挂空约束器。

**咬测四条**：钉死值改成 2 红 1；`setContentOwned(editor,false)` 红 1（细节 416x234，外框没跟）；
去掉 constrainer 委派红 2（1200x900 没夹住）；委派返回空红 2。

构建零 error 零 warning；最终 **1173 ALL PASSED / 0 FAIL**。

## 帧

48 张。与 P121 比 29 张逐字节相同、19 张不同；同二进制两遍自差 17 张。
多出的 `clipauto` 只差 1 像素；`selectmark` 的 180 像素全在 x≈31..84 / y≈107..292 的机架
电平条抖动带内（p119→p120→p121 一路都在抖）。**本轮没有改绘制代码**。

## 留给你的确认

headless 跑不出真实 VST3 的 HWND，也没有 `WM_DPICHANGED`。这里证明的是宿主这一侧的两套尺寸
已经并成一套，不等于双屏黑边一定消失。真机上如果还有黑边，下一步加的是「显示设备变化之后
按编辑器尺寸重同步外框」，不要去动绘制。

# P123 — 黑边还在：尺寸对了，通知没发

用户只回了三个字：「黑边还在」。P122 预言的那一段真的发生了。

## 诊断

P122 把 constrainer 并成一套，也保住了 `setContentOwned(editor, true)` 那条「编辑器改、外框跟」。
但跨屏 DPI 变化的时序是：**原生 HWND 按新 `nativeScaleFactor` 重算了尺寸，JUCE 编辑器的逻辑 bounds
一个像素没动**——`childBoundsChanged` 根本不触发，外框和编辑器「尺寸一致」（都是旧值），而原生
view 已经按新 DPI 画在另一块物理区域上；露出的仍是 `ViewComponent::paint()` 里那块黑。
**尺寸一致不等于 view 重画过。**

## 改法

`PluginEditorWindow::resyncFrameToEditor()` 三件事：

1. 外框 `setSize` 到 `editor 尺寸 + 原生边框`——**编辑器是权威，外框是跟随者**，反过来拖外框会把插件
   挤到它不愿接受的大小。
2. 编辑器 bounds 与 content 区域不一致就 `setBounds`。
3. **bounds 已经一致时反而关键**：同尺寸的 `setBounds` 不发 resized 消息，VST3 的
   `componentMovedOrResized` 收不到，`onSize` + `updateHWNDBounds` 全不跑。故意 `+1 px` 再设回，
   让通知链走两次。这一步是真机上真正把黑边擦掉的那一下（咬测 M2 精确红 1：`0 次 resized`）。

两个触发口：`moved()`（跨屏那一刻）+ 2 Hz 轮询（DPI 变化发生在窗口静止时、或 move 早于
`WM_DPICHANGED` 到达）。两者都只做 `checkDisplayScale()`：拿
`getDisplayForRect(getScreenBounds())->scale` 与上次的值比，**没变就什么都不做**——轮询不能每秒
改两次编辑器尺寸。`simulateDisplayChangeForTest()` 把基线设成不可能值，headless 才有得咬。

两个 JUCE 细节：`Displays::Display` 的字段是 `scale`（double），不是 `scaleFactor`；
`Component::setBounds` 系列**不是虚函数**，自检的 spy 挂在 `resized()` 上——那恰好也是 VST3
收到通知的同一时刻。

## 自检 1173 → 1181（+8）

合成编辑器装好 / 黑边前提成立 / 重同步后 content 与编辑器精确相等 / 外框尺寸正好是编辑器加边框 /
编辑器变大外框跟着 / 尺寸已对仍发两次 resized / move 事件也触发 / 无界面插件走同一条路不出事。

**咬测四条**：掐轮询红 3、掐 nudge 红 1、掐外框跟随红 2、掐 move 触发红 1。

构建零 error 零 warning；最终 **1181 ALL PASSED / 0 FAIL**。

## 帧

49 张。与 P122 比 29 张逐字节相同、20 张不同；同二进制两遍自差 19 张。多出的 `clipauto` 只差
**1 像素** `(210,224)`，且两遍之间为 0——P122 日记里记的同一个抖动。本轮零绘制改动。

## 留给你的确认

headless 里没有第二块显示器、没有真实 VST3 HWND，也就没有 `WM_DPICHANGED`。这里证明的是
「显示变化 → 外框以编辑器为准 → 尺寸没变也发一次通知」这条宿主侧链路成立。**真机黑边是否真的
消失，还得在双屏上拖一次**。如果还在，下一步该看的是具体哪个插件的 `checkSizeConstraint` 在 DPI
变化后把尺寸夹到了别处，而不是继续改宿主外框或绘制。
