## Phase 83 — 插件延迟补偿（PDC）

**动因**：上一轮评估里我自己点出来的第一条硬伤——全工程没有 `setLatencySamples` 也没有任何延迟
补偿，而 `fx::Type::vst` 是可以在通道插入上挂第三方 VST3 的。一个带前瞻的限制器挂在鼓总线、
人声总线空着，鼓就晚几毫秒，而且**没有任何推子能把它推回去**。用户听到的是"这软件混音不对"。

### 一、控制台只有一种汇合，所以只有一个地方要答案

不是"每条路径各算一个延迟"那么含糊。读渲染链可以看到，整块音频只有三处信号相遇：
子通道加进父通道的总线、通道加进主输出、bypass 总线加进主输出。**并行路径只在这些点上产生**，
所以补偿也只在点上做。

`Audio/PdcDelay.h` 里的 `pdc::solve` 把这件事写成一张纯函数表：

- `own[c]` —— 这条通道的插入链总共多晚（`PluginHost::getLatencySamples` 求和，内置效果全是 0）。
- `entry[c]` —— 这条通道**入口**应有的事件时刻，等于最慢的孩子结束的时刻（没有孩子就是 0）。
- 返回值 —— 控制台总延迟；`slide[c]` 只给"直接去主输出"的通道用。

子通道的等待量不放进表，而是汇合时算 `entry[父] - 自己的结束`。**一个事实只有一处**：
表里再存一份 `slideToParent` 就是第二个答案，而两个答案早晚会分叉。

### 二、为什么必须两条延迟线

第一版只想了一条：在通道出口按住它。但汇合有两种情形，而且发生在同一个 block 的**不同时刻**：

- 直达的声音（stage 1 直接写进总线的）到得最早，它要等的是一个**慢孩子**——这在插入链**之前**。
- 处理完的声音在插入之后，它要等的是**更慢的兄弟**——这在插入链**之后**。

一条线只能记一份历史；第二处 push 会把第一处的覆盖掉。所以 `pdcEntry[c]` 和 `pdcExit[c]` 各一条。

### 三、它能上线的唯一理由：零延迟时逐位相同

没有任何插件报延迟 ⟹ 每张表都是 0 ⟹ `maxPdcLatency == 0` ⟹ 渲染里三个 `if` 一个都不进，
走的是 P82 那条路径，**逐样本相同**。这条退化性质是整个改动的安全性来源，所以给它单独一条断言
（`A console with no late insert compensates for nothing`），并且不许有人给总延迟加"至少 1"的兜底。

### 四、这一轮最花时间的是"让路径真的跑一次"

写完发现：无头自检加载不了 VST3，于是补偿代码在自检里**一次都不会执行**——数学有断言，
渲染没有。第一次咬测（把总延迟强改成 `max(1,…)`）结果很有意思：7 条**别的功能**的音频测量
断言一起挂了。这既证明路径确实在真实渲染链上，也暴露了问题——那些断言不该承担这个职责。

于是加了一个明确的口子 `setInsertLatencyForTest(channel, samples)`，只在发布期折进 `own[]`。
有了它才写得出端到端断言：给一条**静默**通道强加 32 采样延迟，整个混音必须逐样本后移 32。
两条：bypass 总线一条、过通道一条。咬测确认互不掩护（各自只挂自己那条）。

### 五、断言与咬测

新增 9 条，723 总，全绿：

- 一条晚通道让整个控制台变晚（`total 96`）；
- 其它路径等待的时长正好是差额（`slides 0/96/96/96`）；
- 父通道从它最慢的孩子结束处开始（`entry 2 = 50, total 80`）；
- 只有快的那个孩子在汇合点等（`waits 0/50`）；
- 没有延迟就不补偿（`total 0`）；
- 延迟线跨块交还它收到的块（`first 1.00, last 4.00`）；
- 没有 VST3 插入的会话报 0 延迟；
- bypass 总线整体后移 32（端到端）；
- 过通道的路径整体后移 32（端到端）。

咬测 5 处：`solve` 不让子通道按住父通道 → 2 条挂；延迟线忽略 delay → 1 条挂；总延迟强制非零 →
9 条挂（含 7 条别的功能的测量，见上）；bypass 不等 → 1 条挂；通道汇合不等 → 1 条挂。
逐处还原，md5 校验一致，收尾 723/0。

### 六、边界

- **容量 2048 采样（≈42 ms @48k）**，超过的插件被夹住。这是用户唯一能察觉的边界。
- **总延迟不做补偿**：整条路径都晚 `maxPdcLatency`，播放时听不出来，但走带位置比声音早同样多。
  要修就得同时动录音对齐和播放头显示，是另一件事。
- **乐器插件（VSTi）的延迟没算**：它们不在插入链上，算进来要按 slot 分缓冲区。多数合成器报 0。
- **主输出插入的延迟没有补偿**：它对全部路径是同一个常数。
- 无头自检仍然加载不了 VST3，所以"真插件报 12000 采样"这个场景只有夹取逻辑被断言过。

## Phase 84 — 崩溃恢复与自动保存

**动因**：上一轮评估里点出的第二条硬伤。74k 行、88 个文件、单人开发——丢一次工程就可能是最后一次。
在这之前，"未保存"只存在于内存里：撤销历史是整工程快照，但一个都没落过盘，进程一走全没了。

### 一、这件事不需要新的序列化

editor 已经有 `captureState()`（整篇会话 → 一个字符串）和 `restoreState()`（字符串 → 会话），
撤销就是这两个函数。所以"扛住崩溃"不是格式问题，是两个时机问题：**什么时候把这个字符串写到某个地方**，
以及**什么时候敢相信它**。

于是这一阶段的真正内容是一句不变量：

> **副本存在 ⟺ 这份会话有未保存的编辑，并且进程没能正常收尾。**

所有规则都是为了让这句话成立：保存 → 删；用户点「不保存」→ 删；载入别的工程 → 删（那些改动被放弃了）；
正常关闭且无改动 → 本来就没有。于是它唯一能活下来的方式就是崩溃。

这条链子断一环，功能就变成制造重复（该删没删，下次启动拿旧东西诱惑你）或制造丢件（不该删删了）。

### 二、`Util/Recovery` 全是纯函数，弹窗只有一层胶水

`getFileFor` / `inspect` / `write` / `readProjectPath` / `listIn` / `discard`。会错的从来是判据，
不是弹窗，所以判据要能被断言，而弹窗（真窗口里那个模态框）无头跑不起来也没关系。

`inspect()` 给四个答案：`none` / `unusable`（空或不是会话文档）/ `stale`（不比工程新）/ `offer`。
两条判据值得单独说：

- **工程不存在（从未保存）→ 一定 offer**。那是没有任何其他地方存着的场景，也是唯一真正救命的场景。
- **打平算 stale**。同一秒说不清谁新；不打扰比赌一条改动便宜。

### 三、三个容易被当成"实现细节"的决定

1. **文件名带路径 hash**（FNV-1a over full path）。两个都叫 `song.atomic` 的工程不能共用一个副本，
   否则第二个会覆盖第一个正要救的东西。唯一接受的冲突是两个从未保存的窗口（都是 `untitled`）——
   文件名无法区分两个无名会话，而每次启动随机后缀会让"这是哪个"从含糊变成不可回答。
2. **副本仍是工程**。根元素只多加 `recoveryOf` / `recoveredAt`，解析器忽略其余。用户最后的逃生手段
   就是拿文件浏览器打开它——所以它必须一直是能打开的。
3. **原子写靠 `File::replaceWithText`**，它走 JUCE 的 `TemporaryFile`（同目录隐藏临时文件 + 改名）。
   写一半崩只丢这一次更新，绝不留下半截。这条比"记得 deleteFile"重要得多：P82 那张旧图的教训是
   `createOutputStream` 会追加，而这里如果追加，恢复到的东西会是两次会话拼起来的。

### 四、最容易犯的错：把副本当成工程

`saveProjectToFile(file)` 最后一行是 `currentProject = file;`。自动保存要写的东西和它**长得一模一样**，
所以最省事的实现就是复用它。后果不是多存一个文件，是 `currentProject` 指向了恢复目录：
之后 Ctrl+S 不再问路径（"已经有一个了"），歌被存进 Rescue 文件夹，真正的工程文件停在旧版本。
用户不会立刻发现，因为标题栏还写着工程名。

所以 `recovery::write` 是一条完全独立的路径：不碰 `currentProject`、不更新 `savedStateText`、
不进撤销历史。反方向同理——`recoverFromFile` 的身份**从副本里读回来**，因为文档里根本没有
"上次打开的是哪个工程"这种记忆。

### 五、默认关闭，因为无头运行会删用户数据

第一版写的是"默认开启"。然后想起 `renderHeadlessReport()` 开工第一件事就是
`saveProjectToFile("demo.atomic")`——而"保存成功"在新设计里意味着删恢复副本。于是每跑一次
`--snapshot` 就会删掉用户真正未保存的工作，而这条路径每天跑几十次。

改成 `recoveryEnabled = false`，只有 `Main.cpp` 的 `MainWindow` 构造里打开。改完专门验证了
`Documents/AtomicDAW/Recovery` 不存在——说明早退真的生效，不是"建了空目录但没写东西"。

### 六、断言与咬测

新增 19 条，742 总，全绿。分四组：

- **身份**：扩展名与 `project::fileExtension` 一致；同名不同目录 → 不同副本；未保存会话固定 `untitled`。
- **`inspect`**：缺失 / 垃圾 / 空 → 不 offer；工程不存在 → offer；打平 → stale；更旧 → stale；更新 → offer。
- **`write`**：自动建目录；带 `recoveryOf` / `recoveredAt`；**写出的东西仍是 `project::fromXmlText` 认的工程**
  （2 notes at 120）——这条是"副本可被手动打开"的证明。
- **端到端**：`recoverFromFile` 把 2 个音符带回来、身份从副本读回、**仍然算未保存**（`dirty`）。

咬测 4 处，**第 4 处第一版打偏了**：把 `dirtyCache = (...)` 改成 `false`，742/0 一条没挂。
因为 `hasUnsavedChanges()` 会当场从 `captureState()` 重算——我咬的是一个马上被覆盖的缓存。
改成咬真相（`savedStateText = history.front()`，即"恢复完顺手当成已保存"）才精确命中 `clean`。
这条写进了 PITFALLS P84-A：**咬测咬不中，先问"我改的是真相还是它的缓存"**。

其余三处：`inspect` 的 `<=` 改成 `<` → 1 条（tied）；写盘不写 `recoveryOf` → 3 条
（属性、扫描、恢复后的身份）；文件名丢掉路径 hash → 1 条（两个 `song.atomic` 撞名）。
逐处还原，md5 校验一致。

### 七、边界

- **窗口里那个模态框没被自动化验证**：无头跑不起消息循环，所以 `offerRecoveryIfAny` 的
  "弹没弹"只能人眼确认一次。它下面的判据全在纯函数里。
- **未保存会话只有一个副本位**：两个未命名窗口同时编辑会互相覆盖。见上，文件名无法区分它们。
- **只 offer 最新那一份**：更早的副本不删也不列菜单，只在对话框里报个数并给出目录路径。
- **`Recovery/` 从不自动清理旧工程**：删工程留下的副本会一直躺着，直到下次启动被判 stale。
- **总延迟那一类问题不涉及**：恢复的是文档，不是音频状态；恢复后走带停在 0、插件重新加载。

## P85 — 钢琴窗拆成十一个 TU / 机架卡片双击开音源界面

### 一、为什么拆，拆的是什么

`Source/UI/PianoRollComponent.cpp` 是 13,125 行一件东西，占全部 UI 代码的四成。改一行采样框
要让整篇模板化的 JUCE 代码重新实例化，改一个菜单文字也一样。这不是审美问题，是"每改一行
付一分半分钟"的问题。

拆的办法是**文件边界，不是类**。C++ 允许一个类的成员函数分散在多个翻译单元里定义，所以：

- 不动头文件一个字符（`PianoRollComponent.h` 2,301 行原样）；
- 不需要 friend、不需要传指针、不存在"两个对象互相问状态"；
- 316 个函数按主题搬，一个文件一个主题。

十个新文件和它们的分工写在 `REFERENCE.md` 的「钢琴窗的文件布局」里，这里只记原则。

### 二、怎么保证"一个字没变"

脚本按顶层块切分（`^[A-Za-z_]` 开头 + 花括号深度回零 = 一个块），每块连同它**上面**的
注释/空行一起归属，所以文件从头到尾被完整覆盖：**13109 行全部分配，一段不剩**。

然后验收不是看编译，是**逐行比对**：

```
原文 13,125 行 → 10,493 个非空行
新文件（11 个 cpp + internals.h）拼起来做多重集，允许两种规范化：
  ① internals 里的定义多了 `inline ` 前缀
  ② 两处裸 `namespace` 包裹换成了 `namespace roll`
剩 5 行差异，全是预期（1 个 include 的尾注 + 2 处 namespace + 2 个闭合括号）
```

这一步第一次跑出来是 8 行差异，多出来的三条是 `// Phase 82: one row, two buttons` 和两条
`//====` 分隔线——它们坐在段**前面**，而 internals 的生成只从 `namespace` 那一行开始取。
编译器当然不报错。补回去之后才敢提交。

### 三、共享层

十三件东西被两个以上 TU 用：`boldFont` / `groupLabelText` / `curveCellFitsText` /
`addCurveItems` / `addCurveVerbs` / 三个 `*RouteLabel` / `drawKnobGlyph` / `neutralCurveValue` /
`uniqueGroupName` / 两个 `modTarget*`，外加九个调色板别名和一堆菜单 id 常量。全部搬进
`UI/PianoRollInternals.h`，`namespace atomic::roll`，**每个定义 `inline`**，每个 TU 顶部
`using namespace roll;`。

留在各自 cpp 的三个匿名 namespace 是判断的结果，不是遗漏：画笔/橡皮光标图（只有 core 用）、
`membersDescription`（只有剪贴板用）、`subEnvelope`（只有 `splitSamplesAt` 用）。
判断标准是"几个 TU 用"。改 internals 要重编十一个 TU，比留在主题文件里贵三倍。

### 四、收益（实测，不是估算）

- 改 `PianoRollSampleDraw.cpp`（1,028 行）→ 全量构建 **22.4 秒**。
- 拆分前同样的改法是 13,125 行一个 TU，量级 5–8 分钟。
- 最大的单个 TU 现在 1,718 行（`PianoRollInput.cpp`）。

### 五、机架卡片双击

`RackPanel::handleDoubleClick` 原来只有一句"双击名字 → 改名"（P79），其他位置 `return`。
现在：

```cpp
if (getNameBounds (index).contains (pos)) { beginRenameSlot (index); return; }   // P79 原样
if (getViewArea().contains (pos) && ! isOverCardControl (index, pos))
    onCardDoubleClicked (slot->id);                                            // P85 新增
```

`isOverCardControl` 排除 caret / × / S / M / 波形 pill / 只变调 / 拉伸 / → 输出 / 两个推子的
`expanded(0, 6)` 带。**折叠卡的 caret 必须单独先测**——折叠之后 `collapsed` 分支一律返回 false，
会把 caret 一起放行，double-click 折叠键就变成开窗。

宿主侧把原菜单第 41 项的逻辑抽成 `MainComponent::openSlotEditor(slotId)`：

### 六、自检：742 → 753

十一新条：面板级七条（空白点存在、上报槽 id、第二张卡报自己的 id、双击名字仍只改名、
双击静音键是两次切换、折叠卡也能开、页面空白不上报）+ 宿主级四条（内置合成器答 false、

   (1 次上报 / 静音 0 -> 0)」。真。

## Phase 86 — 采样路径相对化与重定位

工程文件里的 `path` 一直是绝对路径。改个文件夹名、拷到另一台机器、把工程发给别人，
每一个采样块都指向空处，波形画成"缺失"，唯一的修法是逐个重新导入。
**一个工程离不开它被做出来的那台机器，谈不上可携带。**

### 一、模型只存绝对，相对只是文档的形式

`SampleEvent::path` 一个字节没变。变的是 `ProjectIO` 写出去的那个字符串。
`Model/SamplePath.h` 是唯一规则层，纯函数，不碰模型。

一个 `juce::File("media\\kick.wav")` 会被下一个拿到它的人按**进程当前目录**解释。
所以"存成相对的"这句话只能出现在序列化的那一刻，不能出现在内存里。

### 二、相对路径必须解得回原文件才写

`toStored()` 算出候选 → 用读盘时**同一个** `resolve()` 跑一遍 → 答案等于原文件才采用。
过不了就退回绝对。跨盘、符号链接、解析后落到别处的 `..` 链全部过不了这一关。

结果：**永远正确，只是不那么好搬**。这个顺序是不能反的——先求好搬，就会得到一批
"看起来很短、打开就找不到"的工程。

顺带纠正一个我一开始想反的地方：**工程外面的文件也写成相对**（带 `..`），
只要解得回来。分界线不是"在不在工程目录里"，是"**解不解得回来**"。

### 三、读盘时把修好的位置写回模型

找不到**也写绝对**。否则下一次 Ctrl+S 又把那条死路径存一遍，"修好"只维持一个会话。

这条是咬测第三轮抓出来的真 bug：第一版在加载失败时把 `media\kick86.wav`
留在了模型里。**"回落"和"身份"是两件事**——判定用哪个文件可以层层回落，
但那个答案一旦非空就必须是绝对的。

### 四、重定位只认用户挑的目录

`relinkSamplesTo(folder)`：`FolderIndex` 用**文件名**配对，深度上限 6 层，同名多个取先
找到的。把整块磁盘扫成索引不是"更好的体验"，是一次几十分钟的卡死。

`offerSampleRelink()` 在 `loadProjectFromFile` 末尾问一次，**默认关闭**
（`setSampleRelinkPromptEnabled`）。理由和 P84 的恢复一模一样：`renderHeadlessReport`
开工第一件事就是 `saveProjectToFile`，一个会动用户文件的默认值在无头运行里是定时炸弹。

恢复副本里的相对路径以 `recoveryOf` 指向的工程为基准，**不是**副本自己所在的
`Recovery/` 目录——所以 `restoreState` 多了一个 `projectFile` 参数。

### 五、自检：753 → 765

分三组：写盘选哪种路径（5）/ 找不到怎么救（3）/ 端到端存盘搬家（4）。

咬测四次，三次有收获：
1. `toStored` 恒返回绝对 → 挂 3 条。
2. `resolve` 不认相对路径 → 挂 2 条。
3. 去掉"旁边同名回落" → 诊断打出 `media\kick86.wav`，**暴露模型被污染**（上面第三节）。
4. 第二条断言原本只写"往返一致"——**所有路径都退回绝对时它照样过**。
   补 `&& ! juce::File::isAbsolutePath (inside)` 才从挂 3 条变挂 4 条。

"往返一致"是最弱的一类断言：它证明不了选对了形式，只证明没有把数据弄坏。

## Phase 87 — 循环区间

"循环"在这之前只有一个意思，而且不是个选择：走带**永远循环整首**，因为回绕点就是
`lengthBeats`，没有别的东西能命名一个拍。听成品时这是对的，做音乐时是错的——
"把这八小节反复放，我改鼓"是整个活动里重复次数最多的手势。

### 一、区间的不变量全是关于顺序与最短

`Model/LoopRegion.h`（header-only）：
- 起点永远在终点之前——谁从哪个方向拖都一样；
- **不短于 `minLengthBeats = 0.25` 拍**。一次误点不该做出一个在两采样之间反复抽搐的循环；
- 永不小于 0。拍 0 是时间线的开始，跑到前面去等于回绕到没有音频也没有网格的地方。

### 二、开关与数字分开

关掉循环**不许忘记位置**：关掉听一遍再打开，要的还是那八小节，不是默认值。
所以磁盘上 `loop="0"` 时两个拍子照样写。

渲染侧关闭时 `wrapStart/wrapEnd` 退化成 `[0, length)`，**就是 P87 之前的整首循环**。
老行为逐位不变——这是它能上线的唯一理由，和 P83 的"零延迟时逐位相同"是同一条纪律。

`isUsable()`（`enabled && 长度够`）是唯一判据。少判它一次，后果见下。

### 三、标尺上那 7 个像素

第一版做成 `ui::px(12)` 加"循环"两个字。截图一看，`0:06.0` 被盖住半行。
标尺上每个像素都在说话（拍号、小节线、时间），新带子只有"贴底边"这一种活法。

改成 `ui::px(7)`、去掉文字，把"这是个循环"挪到**车道底色 + 两条竖线**（`drawGridLines`
开头），那里是空的。

### 四、关闭状态也画括号：18 张快照凭空多一个虚框

`drawRuler` 里只判了 `! bar.isEmpty()`，没判 `isUsable()`。`LoopRegion` 的默认值
`0..4` 是合法的，只是 `enabled=false`——于是**每一个空白工程**的标尺上都出现了循环括号。
视觉回归从 20/29 掉到 2/29 才发现。

**"默认值合法"不等于"默认值可见"**。默认构造出来的是"还没被用户说过话"，一个像素都不该占。

### 五、`-loop` 快照必须排最后

`createLoopSnapshot` 会改会话状态（打开循环、设区间），放在序列中间就会把它之后拍的
每一张图都染上循环底色：回归 13/29 → 挪到最后 → **20/29 逐字节相同**，
剩 9 张正是已知抖动集（`mixer` / `recovery` / `selectmark*` / `sampler` / `groupauto` /
`slotparam` / `mixer-narrow`）。

会改状态的快照函数必须排在最后。这和 P84 的恢复、P86 的重定位弹窗是同一类问题的三种表现。

## Phase 88 — 节拍器与预备拍

"点击"是这台机器上最便宜的功能，也是要求最苛刻的一个：耳朵原谅一个晚 5 ms 的音符，
不原谅一个晚 5 ms 的点击——**点击和演奏错开就是那个错误本身**。所以它不能由定时器驱动，
只能由拍和每块的 `beatsPerSample` 驱动，而且每一下必须落在它该在的那个采样上，
不是落在它碰巧所在的那一块的块首。

### 一、`Audio/Metronome`：三个决定

`Metronome.h/.cpp`（新文件，LF）。三个决定各自对应一个"顺手会写错"的写法：

1. **混进走带的块，绝不混进 `renderInto`。** 导出、分轨、离线分析都是 `renderInto` 那条路，
   所以"导出里没有点击"是**结构性的**，不是靠记得关。咬测把 `renderWindow` 污染一次，
   同时挂 27 条，正反两面都证过了。
2. **两个音是同一个形状，只是音高不同。** 小节第一拍 1600 Hz，其余 1000 Hz。
   给重音换个波形就是第二个要调的参数；音高是每个乐手本来就在听的那个区别。
   两条形状都是 `sin × exp(-t/0.0035)`，外加 **0.5 ms 淡入**——不是装饰：正弦本身从 0 起，
   但包络从 1 起，于是第 0 个采样是 0、第 1 个采样是一个可观的台阶，
   那个台阶就是"刺"而不是"准"里的宽带成分。
3. **四个声部，不是一个。** 一击 12 ms，一块可以 46 ms，快速度下一块能落三拍。
   一个声部会把上一击从衰减中途切断，听起来是踉跄。满了丢**最老**的（`position` 最大的）。

分句：`for (int beat = ceil (fromBeat - 1e-9); beat < toBeat; ++beat)`。
那个 `-1e-9` 是为了让**正好落在块边界上**的那一拍只算一次——否则它是上一块的最后一拍、
又是下一块的第一拍，重音会响两遍。

### 二、`force`：数拍的人不能因为没开节拍器而听不到数

`render(…, force=false)` 里 `if (! force && ! isEnabled()) return;`。
预备拍传 `true`。这条看着像让步，其实是语义：用户点了"录音"，他要的就是被数进去，
节拍器开关管的是"演奏时听不听点击"，不是"能不能被数"。

音量是它**自己**的（`setVolume`），不骑主推子。骑主推子意味着动一下混音台就改掉了
演奏者的时间参考。音量 0 时**先 `silence()` 再返回**——否则衰减中途把音量拧到 0，
尾巴会冻在那儿，拧回来接着响。

### 三、预备拍：数的是下拍**之前**那几拍

`renderPreRoll` 每一块**不改 `positionBeats`**。所以"数拍期间歌曲没动"是构造性的，
不是"我小心地没有调用 play"。若做成"先播放再数四拍"，`recordStartBeat` 就是个谎。

数完在**同一个块里**交接：`cancelPreRoll()` 之后把剩余的 `numSamples - segment` 交给
`renderNextBlock`。在块边界交接会往最后一击和第一个音之间塞一个 buffer 的静音，
最多 46 ms，而且随缓冲区大小变——这是那种"在开发机上听不出来"的错。

数拍期间 `blockBeats.store(0.0)`：不这么说，播放头会从一块"正在被数进去"的块往前外推。

`getPreRollBeatsLeft()` 用 `floor(preRollBeat)` 算已数几拍，所以读数从 N 掉到 1，
不是从 N-1 掉到 0。

### 四、录音 skip：在 `RecordBuffer::begin` 里生效，不是"数完再 arm"

`Recorder::begin (samplesToSkip)` → 一个 `std::atomic<int> skipRemaining`，`append()` 里
先按它左移 `sourceOffset` 再写。`startRecording()` 算 `skipSamples = 拍数 × getSecondsPerBeat() × 采样率`。

为什么不"数完再把 tape arm 起来"：那要等一个 timer tick，而 take 会从自己的 downbeat
**之后**开始——第一个音被削掉一点，正是预备拍要避免的那件事。

`startRecording()` 的顺序也是构造性的：先 `playTransport()`（它会 rewind 一个停在线尾的
播放头），再 `startPreRoll`，再读 `recordStartBeat`。反过来读，take 的第一小节会落在
歌根本没去过的地方。

`setPositionBeats` / `AudioEngine::pause` / `finishRecording` 三处一律 `cancelPreRoll()`：
跳走之后还在数的数是别人的拍。

### 五、顶栏：一个 34×28 的按钮，和一次 36 px 的右移

`getMetronomeButtonBounds()` = `getBpmFieldBounds().getRight() + px(6)`，`新建` 跟着右移。
节拍器在音乐上就该在速度旁边，而且那里原本有一段"看着像空地"的缝。

字形画了三次才对：第一版只有"梯形 + 斜线"，8 倍放大一看读成 **λ**。
加**配重圆点**（斜臂末端 3.2px 实心圆）之后才读得出来——没有它，一个上窄下宽的外框
加一根斜线，只是一封信。探针 34px 宽、`halfBase` 6.0 → 6.4、斜臂内收，一起改的。

录音时读数区被盖住，改写成 `预备 N`（`theme::record` 色）。读数区本来就在那儿写
`0:02.0`，不盖住就是两行字叠在一起。

顺带修了一处陈年错：项目名旁的阶段号还写着 `P39`——从 P40 起就没人更新过。现在是 `P88`。

### 一、门禁四条，全判在 ASCII 上

日志里全是中文，而 GitHub runner 的控制台代码页和我们不一样——所以判据一个都不许依赖中文：

1. 退出码 0；
2. `[FAIL]` 行数为 0；
3. 日志里有 `ALL CHECKS PASSED`；
4. PASS 行数 ≥ `env.MIN_CHECKS`（810）。

第 4 条是**唯一能执法"断言只增不减"的地方**。它必须在同一个提交里被调大——它要是一个
有人选的数，不是"这次跑出来多少"；否则它只是在记录，不是在守。

### 二、故意不做三件事，每件都有理由

- **不跑视觉回归**。8 张本来会抖（电平表 / 播放头 / 恢复时间戳），其余依赖 runner 的字体
  与 DPI。在这里做逐字节比较，红了也不是缺陷——**会喊狼的闸门最后一定被人关掉**。
  30 张图照样传 artifact，给人看。这是 P87-E 那条"哪些图允许抖"攒下来的直接后果：
  抖动集清单不是给 CI 豁免用的，是给 CI **不碰**用的。
- **不扫机器上的插件**。`--snapshot` 已经是 `setScanExtraPathsOnly(true)`，只看构建树里那
  两个一次性 VST3。"runner 上一个插件都没装"是正常情况。这条是 P39 就定下的，这一轮才第一次
  真的跑在一台"什么都没装"的机器上。
- **不开 `/WX`**。警告数打进 summary（工程要求零 warning），但不判红：JUCE 头文件里因为
  工具链更新多出一个警告，不是本仓库的缺陷。

### 三、`| Tee-Object` 会把退出码交给 tee

构建那一步原本写成一条：

```powershell
cmake --build build --config Release 2>&1 | Tee-Object -FilePath build.log
```

跑得通、也有日志，**但坏构建会绿着过去**——管道的退出状态是最后一个命令（tee）的，
tee 成功就是成功。接下来红的会是"self-test: not built"，于是一个编译器错误被报成了
"exe 不存在"。

所以每次要在管道里留日志，就得显式查：

```powershell
if ($LASTEXITCODE -ne 0) { throw "build failed (exit $LASTEXITCODE)" }
```

`$LASTEXITCODE` 在管道结束后仍是 cmake 的，只有 `$?` 被 tee 顶掉了。

### 四、CI 跑的形态本地先跑一遍

以前所有快照都是在 `build/AtomicDAW_artefacts/Release/` 里跑的（cwd = exe 目录），
CI 跑在**仓库根**。这两件事可能不通：`addDevPluginPaths` 若是相对 cwd 找插件，
5300 那一片 VST3 断言会全红。

本地实测了一次仓库根运行：**810/0**，VST3 发现"1 instruments / 1 effects"，出图落在
参数 png 的同级目录。所以插件发现是**从可执行文件**往上走的，与 cwd 无关——
这条以前只是代码里写着，现在是验过的。

### 五、缓存

JUCE 走 FetchContent，冷跑是两百多兆的浅克隆 + 全量编译 ≈ 15 分钟。缓存 `build/_deps`
（key 带 JUCE 版本）后 ≈ 3 分钟。缓存整个 `build/` 更快，但 CMakeCache 里的绝对路径与
MSBuild 增量状态跨镜像很容易做出"本地能编、CI 报奇怪链接错"，不值。

### 六、这一轮没动代码

零代码改动，`formatVersion` 仍是 28，断言仍是 810。所以没有咬测——**这一轮的"咬测"是
把门禁的每条判据手动跑一遍**：拿真实日志验 PASS/FAIL 计数、伪造一行 `[FAIL]` 确认它被抓出来、
在仓库根真跑一遍快照。

# Phase 90 — 量化选区

## 一、为什么是这个顺序

上一轮查"拍号与量化"查出来两件事各自缺一块：拍号只有一行 constexpr，量化**根本不存在**
（有的是手势期间的吸附）。量化先做，因为它不碰文件格式，而拍号要动 `formatVersion`。
两件事分开成两阶段，各自有自己的咬测和提交。

## 二、一个纯函数

`Model/Quantize.h`：`nearestGridPoint (beat, grid)` + `apply (beat, grid, strength)`。

- `round` 不是 `floor`：一个早 6 ms 的音，向下取整会把它推到**下一格**。
- 强度是"走过去多少"，0 = 原样退回（逐位相同），≥1 走满。
- 第一版写着 `const double amount = std::min (1.0, strength);` 再判 `amount >= 1.0`。
  咬测把 `std::min` 删掉，**一条都没挂**——早退先接住了所有 `strength >= 1`。
  那行不是防御，是噪声，删了。改成直接用 `strength` 判早退。
- 网格 0 返回原值：调用方忘了设网格时，音符不该被堆到 0 上。

## 三、入口与菜单

`PianoRollComponent::quantizeSelection (gridBeats, strength)`，画布右键菜单 `量化 ▸`：
五档网格（1/32 / 1/16 / 1/8 / 1/4 / 小节，勾在当前）+ 一个 `强度 ▸`（100/75/50/25）。
网格与强度存在组件上——它们属于**工具**，不属于工程。

`moved == 0` 直接返回：不重绘、不产生撤销步。判"算不算动"用 `abs(diff) < 1e-9`，
因为 `round(x/g)*g` 对 `0.1` 这类网格不是逐位相等（差 5e-17），用 `==` 会把
"已经在格上"报成一次移动。这条专门加了一条断言（网格 0.1、音符 0.3 → 0 个移动）。

## 四、编组：这一轮真正的坑

第一版只做了"改起点 + 同步形状"，自检挂了一条：副本从 8.00/8.57 变成 **7.89/8.64**，
而不是 8.00/8.75。形状对了，位置错了一拍误差。

原因：`occurrenceStart` 是**存下来的数**（P62，为的是"删掉最早那个成员不许让整个出现搬家"），
所有拖动路径都会同时挪它（`applyOccurrenceOriginsForMove`），量化不会。而 `syncGroupShape`
按 `副本自己的原点 + 源码的相对形状` 落位——源码的原点还指着成员的旧位置（0.11，而成员已经
到 0.0），副本就整体平移 -0.11。

修法：改完起点先重锚定 `setOccurrenceStart(groupId, occurrence, 该出现的最小成员)`，再同步。
"原点是最好早的那个成员"不是新规则，就是 `occurrenceStart` 缺失时自己 materialise 的算法。

第二件事：同步**无条件**做，包括"整次出现都选中"。`collectTwinsForEdit` 在整次出现时跳过
同步，因为拖动整次出现不改形状；量化改（每个成员按自己的误差归位），跳过就是一个组两份形状。

## 五、自检与咬测

810 → **829**（+19，五组：纯函数 5 / 选区 6 / 采样块 1 / 编组 1 / 菜单 6）。

咬测十处，九处命中（第十处是"删掉 `std::min`"，没挂——见上，那是多余的行，已删除）：

| 咬的什么 | 挂 |
|---|---|
| `round` → `floor` | 7 |
| 去掉强度混合 | 2 |
| 去掉 1e-9 守卫 | 1 |
| 去掉重锚定 | 1 |
| 去掉 `syncGroupShape` | 1 |
| 菜单项恒可点 | 1 |
| 去掉采样块循环 | 1 |
| 小节档写死 4 | 1 |
| `>= 1.0` → `== 1.0` | 1 |

## 六、视觉回归

**25/30 与 P88 逐字节相同**——这一轮一行绘制都没改，符合预期。5 张差异全落在已知抖动集
（`groupauto` / `mixer` / `recovery` / `selectmark-focus` / `selectmark-shell`）。

## 七、边界

量化只动起点（长度是另一件事）；网格没有三连音；lane 不受影响；网格与强度不进工程文件，
`formatVersion` 仍是 28。CI 的 `MIN_CHECKS` 跟着 810 → 829（P89 定的规矩：加断言的那一轮
必须顺手调大）。

# Phase 91 — 拍号是工程属性

## 一、这一行终于要变成值

`Util/SharedRules.h` 里那行 `constexpr double beatsPerBar = 4.0` 从 P56 就在，注释自己写着
"there is no time-signature setting yet; when there is, this is the one line that becomes a
value"。八十八个阶段之后它变成值。四个读者：标尺的小节线与小节号、"复制到后一小节"的
落点、节拍器的重音、量化菜单的「1 小节」（最后这个 P90 已经把它收成了参数，所以这一轮
只要前三个）。

## 二、规则搬到 `Model/Meter.h`

`Util` 头文件看不见 `Model` 的值，所以 `beatsPerBar` / `nextBarLineAfter` /
`barLineAtOrAfter` 从 `SharedRules.h` **整条删掉**（不留转发壳，"唯一实现"不能有两个地方），
搬到新的 `Model/Meter.h`：`clamp (1..16)` + 三个算术函数，全是 `inline` 纯函数。
两个方向不能互换——`nextBarLineAfter` 是"我要往后走"（先按网格吸，再找**严格更晚**的线），
`barLineAtOrAfter` 是"我从这儿开始放"（`- 1e-9`：正好在线上就答这条）。

## 三、一个值，三个读者

`MainComponent::setBeatsPerBar` 是唯一入口，它推两处：`pianoRoll.setBeatsPerBar`
（标尺与小节号）和 `applyMetronomeSettings`（重音）。**故意不调 `modelChanged()`**：
加载与会话重置也走这条路，那两处不是编辑，快照会平白给下一首歌一个撤销步；撤销步由
菜单回调登记（`if (beatsPerBar != before)`）。

`PianoRollComponent::gridLineAlpha` 因此多了一个参数。它是 `static`，`(double) beatsPerBar`
在 static 成员里没有 `this`——两个绘制调用点显式传 `beatsPerBar`，测试钩子
`gridLineAlphaForTest` 同步加第二个参数。

## 四、文件格式 v29

`<Transport>` 从"有循环才写"改成**永远写**：拍号是工程的属性，不是循环的附件。
有循环才写，会让「4/4 无循环」和「3/4 无循环」序列化成同一份文档——保存一次就丢拍号。
`beatsPerBar` 缺失 = 4/4，所以 v28 及更老的文件零迁移。

**读侧先无条件赋默认、再查表**。第一版只写了"元素在、属性不在"那一半
（`getIntAttribute` 的默认参数），咬测当场揭穿：把默认参数删掉、把 `hasAttribute` 包上，
一条都没挂——因为外层那个无条件赋值已经填好答案了。真正承重的是外层：
一首没循环的 v28 歌**根本没有 `<Transport>` 元素**，那时 `getIntAttribute` 不会被求值。

## 五、两个门

1. **标尺左上角那格**（`getMeterCornerArea()` = 键盘宽 × 标尺高 = 96×42）。读数从
   `1 小节` 改成 `4/4`，下一行 `2.00 s` 是小节秒数（`beatsPerBar × 60 / bpm`）。
   这一击在 `handlePress` 里排最前并 `return`——少了 `return`，同一击会继续落到标尺上
   把播放头拖到 0。
2. **节拍器菜单里的「每小节拍数」**（2/4…12/4，id = `300 + beats`）。角落那格写着 `4/4`
   却什么也不说，没人会为了找设置去点它；节拍器菜单本来就在工具栏上，而它上面的
   「预备拍」已经按小节数了，两个放一起。

两个门都调 `setBeatsPerBar`，一处数据两个入口（P79 的规矩）。

## 六、自检与咬测

断言 829 → **850**（+21，六组：纯函数 7 / 钢琴窗 5 / 角落 2 / 窗口与菜单 1 /
工程文件 5 / 两个读者 2）。`MIN_CHECKS` 同步 829 → 850。

咬测十一处，**每一处都挂在该挂的那几条上**：

| 变异 | 挂 |
|---|---|
| `nextBarLineAfter` 写死 4 | 3 |
| `clamp` 不夹 | 2 |
| 没有循环就不写 `<Transport>` | 2 |
| 读侧不再预先赋默认值 | 1 |
| 读侧不再给属性留默认值 | 1 |
| 钢琴窗 `setBeatsPerBar` 不夹 | 1 |
| 小节线重量写死 4 | 1 |
| 角落不再吃那一击 | 1 |
| 复制到后一小节用默认拍号 | 2 |
| 量化菜单的「1 小节」用默认拍号 | 1 |
| 节拍器不推拍号 | 1 |

第一遍跑出来的是**失败数一轮比一轮多**：还原用 `shutil.copy2`，它连 mtime 一起复制，
还原后源码比刚才的 `.obj` 还旧，MSBuild 判定"没变"直接跳过，上一咬的变异全留在里面。
加一句 `os.utime(path, None)` 之后才看清每一咬各自挂在哪。

## 七、视觉回归与边界

**13/31 与 P90 逐字节相同**。19 张差异分两类：**11 张**是角落那格的 24×9 文字框
（`1 小节` → `4/4`），**7 张**落在已知抖动集（`mixer` / `mixer-narrow` / `recovery` /
`sampler` / `groupauto` / `selectmark*`）。判"是不是有意的改动"用 bbox 不用 md5：
面积、位置、形状不对就是出了别的事。

边界：一拍就是一个四分音符，2/4…12/4 行，**6/8 不行**（要先有附点四分的脉）；
变拍号（歌里换拍号）没做，拍号现在是**一个**工程值，不是一张表。`formatVersion` 28 → 29，
下一个要存的东西（节拍器的开关/音量/预备拍）就得升 30。
