## Phase 83 — 插件延迟补偿（PDC）

**动因**：上一轮评估里我自己点出来的第一条硬伤——全工程没有 `setLatencySamples` 也没有任何延迟
补偿，而 `fx::Type::vst` 是可以在通道插入上挂第三方 VST3 的。一个带前瞻的限制器挂在鼓总线、
人声总线空着，鼓就晚几毫秒，而且**没有任何推子能把它推回去**。用户听到的是"这软件混音不对"。

### 一、控制台只有一种汇合，所以只有一个地方要答案

不是"每条路径各算一个延迟"那么含糊。读渲染链可以看到，整块音频只有三处信号相遇：
子通道加进父通道的总线、通道加进主输出、bypass 总线加进主输出。**并行路径只在这些点上产生**，
所以补偿也只在点上做。

`Audio/PdcDelay.h` 里的 `pdc::solve` 把这件事写成一张纯函数表：

- `own[c]` —— 这条通道的插入链总共多晚（`PluginHost::getLatencySamples` 求和，内置效果全是 0）。
- `entry[c]` —— 这条通道**入口**应有的事件时刻，等于最慢的孩子结束的时刻（没有孩子就是 0）。
- 返回值 —— 控制台总延迟；`slide[c]` 只给"直接去主输出"的通道用。

子通道的等待量不放进表，而是汇合时算 `entry[父] - 自己的结束`。**一个事实只有一处**：
表里再存一份 `slideToParent` 就是第二个答案，而两个答案早晚会分叉。

### 二、为什么必须两条延迟线

第一版只想了一条：在通道出口按住它。但汇合有两种情形，而且发生在同一个 block 的**不同时刻**：

- 直达的声音（stage 1 直接写进总线的）到得最早，它要等的是一个**慢孩子**——这在插入链**之前**。
- 处理完的声音在插入之后，它要等的是**更慢的兄弟**——这在插入链**之后**。

一条线只能记一份历史；第二处 push 会把第一处的覆盖掉。所以 `pdcEntry[c]` 和 `pdcExit[c]` 各一条。

### 三、它能上线的唯一理由：零延迟时逐位相同

没有任何插件报延迟 ⟹ 每张表都是 0 ⟹ `maxPdcLatency == 0` ⟹ 渲染里三个 `if` 一个都不进，
走的是 P82 那条路径，**逐样本相同**。这条退化性质是整个改动的安全性来源，所以给它单独一条断言
（`A console with no late insert compensates for nothing`），并且不许有人给总延迟加"至少 1"的兜底。

### 四、这一轮最花时间的是"让路径真的跑一次"

写完发现：无头自检加载不了 VST3，于是补偿代码在自检里**一次都不会执行**——数学有断言，
渲染没有。第一次咬测（把总延迟强改成 `max(1,…)`）结果很有意思：7 条**别的功能**的音频测量
断言一起挂了。这既证明路径确实在真实渲染链上，也暴露了问题——那些断言不该承担这个职责。

于是加了一个明确的口子 `setInsertLatencyForTest(channel, samples)`，只在发布期折进 `own[]`。
有了它才写得出端到端断言：给一条**静默**通道强加 32 采样延迟，整个混音必须逐样本后移 32。
两条：bypass 总线一条、过通道一条。咬测确认互不掩护（各自只挂自己那条）。

### 五、断言与咬测

新增 9 条，723 总，全绿：

- 一条晚通道让整个控制台变晚（`total 96`）；
- 其它路径等待的时长正好是差额（`slides 0/96/96/96`）；
- 父通道从它最慢的孩子结束处开始（`entry 2 = 50, total 80`）；
- 只有快的那个孩子在汇合点等（`waits 0/50`）；
- 没有延迟就不补偿（`total 0`）；
- 延迟线跨块交还它收到的块（`first 1.00, last 4.00`）；
- 没有 VST3 插入的会话报 0 延迟；
- bypass 总线整体后移 32（端到端）；
- 过通道的路径整体后移 32（端到端）。

咬测 5 处：`solve` 不让子通道按住父通道 → 2 条挂；延迟线忽略 delay → 1 条挂；总延迟强制非零 →
9 条挂（含 7 条别的功能的测量，见上）；bypass 不等 → 1 条挂；通道汇合不等 → 1 条挂。
逐处还原，md5 校验一致，收尾 723/0。

### 六、边界

- **容量 2048 采样（≈42 ms @48k）**，超过的插件被夹住。这是用户唯一能察觉的边界。
- **总延迟不做补偿**：整条路径都晚 `maxPdcLatency`，播放时听不出来，但走带位置比声音早同样多。
  要修就得同时动录音对齐和播放头显示，是另一件事。
- **乐器插件（VSTi）的延迟没算**：它们不在插入链上，算进来要按 slot 分缓冲区。多数合成器报 0。
- **主输出插入的延迟没有补偿**：它对全部路径是同一个常数。
- 无头自检仍然加载不了 VST3，所以"真插件报 12000 采样"这个场景只有夹取逻辑被断言过。

## Phase 84 — 崩溃恢复与自动保存

**动因**：上一轮评估里点出的第二条硬伤。74k 行、88 个文件、单人开发——丢一次工程就可能是最后一次。
在这之前，"未保存"只存在于内存里：撤销历史是整工程快照，但一个都没落过盘，进程一走全没了。

### 一、这件事不需要新的序列化

editor 已经有 `captureState()`（整篇会话 → 一个字符串）和 `restoreState()`（字符串 → 会话），
撤销就是这两个函数。所以"扛住崩溃"不是格式问题，是两个时机问题：**什么时候把这个字符串写到某个地方**，
以及**什么时候敢相信它**。

于是这一阶段的真正内容是一句不变量：

> **副本存在 ⟺ 这份会话有未保存的编辑，并且进程没能正常收尾。**

所有规则都是为了让这句话成立：保存 → 删；用户点「不保存」→ 删；载入别的工程 → 删（那些改动被放弃了）；
正常关闭且无改动 → 本来就没有。于是它唯一能活下来的方式就是崩溃。

这条链子断一环，功能就变成制造重复（该删没删，下次启动拿旧东西诱惑你）或制造丢件（不该删删了）。

### 二、`Util/Recovery` 全是纯函数，弹窗只有一层胶水

`getFileFor` / `inspect` / `write` / `readProjectPath` / `listIn` / `discard`。会错的从来是判据，
不是弹窗，所以判据要能被断言，而弹窗（真窗口里那个模态框）无头跑不起来也没关系。

`inspect()` 给四个答案：`none` / `unusable`（空或不是会话文档）/ `stale`（不比工程新）/ `offer`。
两条判据值得单独说：

- **工程不存在（从未保存）→ 一定 offer**。那是没有任何其他地方存着的场景，也是唯一真正救命的场景。
- **打平算 stale**。同一秒说不清谁新；不打扰比赌一条改动便宜。

### 三、三个容易被当成"实现细节"的决定

1. **文件名带路径 hash**（FNV-1a over full path）。两个都叫 `song.atomic` 的工程不能共用一个副本，
   否则第二个会覆盖第一个正要救的东西。唯一接受的冲突是两个从未保存的窗口（都是 `untitled`）——
   文件名无法区分两个无名会话，而每次启动随机后缀会让"这是哪个"从含糊变成不可回答。
2. **副本仍是工程**。根元素只多加 `recoveryOf` / `recoveredAt`，解析器忽略其余。用户最后的逃生手段
   就是拿文件浏览器打开它——所以它必须一直是能打开的。
3. **原子写靠 `File::replaceWithText`**，它走 JUCE 的 `TemporaryFile`（同目录隐藏临时文件 + 改名）。
   写一半崩只丢这一次更新，绝不留下半截。这条比"记得 deleteFile"重要得多：P82 那张旧图的教训是
   `createOutputStream` 会追加，而这里如果追加，恢复到的东西会是两次会话拼起来的。

### 四、最容易犯的错：把副本当成工程

`saveProjectToFile(file)` 最后一行是 `currentProject = file;`。自动保存要写的东西和它**长得一模一样**，
所以最省事的实现就是复用它。后果不是多存一个文件，是 `currentProject` 指向了恢复目录：
之后 Ctrl+S 不再问路径（"已经有一个了"），歌被存进 Rescue 文件夹，真正的工程文件停在旧版本。
用户不会立刻发现，因为标题栏还写着工程名。

所以 `recovery::write` 是一条完全独立的路径：不碰 `currentProject`、不更新 `savedStateText`、
不进撤销历史。反方向同理——`recoverFromFile` 的身份**从副本里读回来**，因为文档里根本没有
"上次打开的是哪个工程"这种记忆。

### 五、默认关闭，因为无头运行会删用户数据

第一版写的是"默认开启"。然后想起 `renderHeadlessReport()` 开工第一件事就是
`saveProjectToFile("demo.atomic")`——而"保存成功"在新设计里意味着删恢复副本。于是每跑一次
`--snapshot` 就会删掉用户真正未保存的工作，而这条路径每天跑几十次。

改成 `recoveryEnabled = false`，只有 `Main.cpp` 的 `MainWindow` 构造里打开。改完专门验证了
`Documents/AtomicDAW/Recovery` 不存在——说明早退真的生效，不是"建了空目录但没写东西"。

### 六、断言与咬测

新增 19 条，742 总，全绿。分四组：

- **身份**：扩展名与 `project::fileExtension` 一致；同名不同目录 → 不同副本；未保存会话固定 `untitled`。
- **`inspect`**：缺失 / 垃圾 / 空 → 不 offer；工程不存在 → offer；打平 → stale；更旧 → stale；更新 → offer。
- **`write`**：自动建目录；带 `recoveryOf` / `recoveredAt`；**写出的东西仍是 `project::fromXmlText` 认的工程**
  （2 notes at 120）——这条是"副本可被手动打开"的证明。
- **端到端**：`recoverFromFile` 把 2 个音符带回来、身份从副本读回、**仍然算未保存**（`dirty`）。

咬测 4 处，**第 4 处第一版打偏了**：把 `dirtyCache = (...)` 改成 `false`，742/0 一条没挂。
因为 `hasUnsavedChanges()` 会当场从 `captureState()` 重算——我咬的是一个马上被覆盖的缓存。
改成咬真相（`savedStateText = history.front()`，即"恢复完顺手当成已保存"）才精确命中 `clean`。
这条写进了 PITFALLS P84-A：**咬测咬不中，先问"我改的是真相还是它的缓存"**。

其余三处：`inspect` 的 `<=` 改成 `<` → 1 条（tied）；写盘不写 `recoveryOf` → 3 条
（属性、扫描、恢复后的身份）；文件名丢掉路径 hash → 1 条（两个 `song.atomic` 撞名）。
逐处还原，md5 校验一致。

### 七、边界

- **窗口里那个模态框没被自动化验证**：无头跑不起消息循环，所以 `offerRecoveryIfAny` 的
  "弹没弹"只能人眼确认一次。它下面的判据全在纯函数里。
- **未保存会话只有一个副本位**：两个未命名窗口同时编辑会互相覆盖。见上，文件名无法区分它们。
- **只 offer 最新那一份**：更早的副本不删也不列菜单，只在对话框里报个数并给出目录路径。
- **`Recovery/` 从不自动清理旧工程**：删工程留下的副本会一直躺着，直到下次启动被判 stale。
- **总延迟那一类问题不涉及**：恢复的是文档，不是音频状态；恢复后走带停在 0、插件重新加载。

## P85 — 钢琴窗拆成十一个 TU / 机架卡片双击开音源界面

### 一、为什么拆，拆的是什么

`Source/UI/PianoRollComponent.cpp` 是 13,125 行一件东西，占全部 UI 代码的四成。改一行采样框
要让整篇模板化的 JUCE 代码重新实例化，改一个菜单文字也一样。这不是审美问题，是"每改一行
付一分半分钟"的问题。

拆的办法是**文件边界，不是类**。C++ 允许一个类的成员函数分散在多个翻译单元里定义，所以：

- 不动头文件一个字符（`PianoRollComponent.h` 2,301 行原样）；
- 不需要 friend、不需要传指针、不存在"两个对象互相问状态"；
- 316 个函数按主题搬，一个文件一个主题。

十个新文件和它们的分工写在 `REFERENCE.md` 的「钢琴窗的文件布局」里，这里只记原则。

### 二、怎么保证"一个字没变"

脚本按顶层块切分（`^[A-Za-z_]` 开头 + 花括号深度回零 = 一个块），每块连同它**上面**的
注释/空行一起归属，所以文件从头到尾被完整覆盖：**13109 行全部分配，一段不剩**。

然后验收不是看编译，是**逐行比对**：

```
原文 13,125 行 → 10,493 个非空行
新文件（11 个 cpp + internals.h）拼起来做多重集，允许两种规范化：
  ① internals 里的定义多了 `inline ` 前缀
  ② 两处裸 `namespace` 包裹换成了 `namespace roll`
剩 5 行差异，全是预期（1 个 include 的尾注 + 2 处 namespace + 2 个闭合括号）
```

这一步第一次跑出来是 8 行差异，多出来的三条是 `// Phase 82: one row, two buttons` 和两条
`//====` 分隔线——它们坐在段**前面**，而 internals 的生成只从 `namespace` 那一行开始取。
编译器当然不报错。补回去之后才敢提交。

### 三、共享层

十三件东西被两个以上 TU 用：`boldFont` / `groupLabelText` / `curveCellFitsText` /
`addCurveItems` / `addCurveVerbs` / 三个 `*RouteLabel` / `drawKnobGlyph` / `neutralCurveValue` /
`uniqueGroupName` / 两个 `modTarget*`，外加九个调色板别名和一堆菜单 id 常量。全部搬进
`UI/PianoRollInternals.h`，`namespace atomic::roll`，**每个定义 `inline`**，每个 TU 顶部
`using namespace roll;`。

留在各自 cpp 的三个匿名 namespace 是判断的结果，不是遗漏：画笔/橡皮光标图（只有 core 用）、
`membersDescription`（只有剪贴板用）、`subEnvelope`（只有 `splitSamplesAt` 用）。
判断标准是"几个 TU 用"。改 internals 要重编十一个 TU，比留在主题文件里贵三倍。

### 四、收益（实测，不是估算）

- 改 `PianoRollSampleDraw.cpp`（1,028 行）→ 全量构建 **22.4 秒**。
- 拆分前同样的改法是 13,125 行一个 TU，量级 5–8 分钟。
- 最大的单个 TU 现在 1,718 行（`PianoRollInput.cpp`）。

### 五、机架卡片双击

`RackPanel::handleDoubleClick` 原来只有一句"双击名字 → 改名"（P79），其他位置 `return`。
现在：

```cpp
if (getNameBounds (index).contains (pos)) { beginRenameSlot (index); return; }   // P79 原样
if (getViewArea().contains (pos) && ! isOverCardControl (index, pos))
    onCardDoubleClicked (slot->id);                                            // P85 新增
```

`isOverCardControl` 排除 caret / × / S / M / 波形 pill / 只变调 / 拉伸 / → 输出 / 两个推子的
`expanded(0, 6)` 带。**折叠卡的 caret 必须单独先测**——折叠之后 `collapsed` 分支一律返回 false，
会把 caret 一起放行，double-click 折叠键就变成开窗。

宿主侧把原菜单第 41 项的逻辑抽成 `MainComponent::openSlotEditor(slotId)`：

### 六、自检：742 → 753

十一新条：面板级七条（空白点存在、上报槽 id、第二张卡报自己的 id、双击名字仍只改名、
双击静音键是两次切换、折叠卡也能开、页面空白不上报）+ 宿主级四条（内置合成器答 false、

   (1 次上报 / 静音 0 -> 0)」。真。
