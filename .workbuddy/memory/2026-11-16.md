# P113 — 折起来的那条带自己也变薄

用户一句话：「折叠之后，整个图层在总览中的宽度也变成一条线的宽度」。

P109–P112 把每条带钉死成 **1/N**：折叠只回答「几行」，从不回答「占多少地方」。于是折起来的层
仍然占着整个 1/N，只在正中间画一条线——上面一半空气、下面一半空气。用户这句话要的是另一半。

## 改法：带宽从「一个只读自己的数」变成「整摞的派生量」

`getOverviewBandBounds` 先数 `folded` / `open`，再：

```
slice = 网格高 / count
thin  = min (16 设计像素, slice)                       // 折起来的带
share = open > 0 ? (网格高 - thin * folded) / open : slice
heightOf(i) = (open > 0 && 折着) ? thin : share
```

两条边仍然各自取整（两种高度混在一张图上时这条更要紧），所以整摞仍然首尾相接铺满网格。

**16 不是新数**：它就是 `drawOverviewColumn` 里那句「一个名字需要 16 px 的条带」，也是折叠
**可逆**的最小高度——小三角是 `min (13, 高度 - 4)`，16 留得下 12 px 的按钮（实测 12）。薄的
代价原本可以是「折完之后左列只剩色带、展开只能走菜单」，这一轮没有接受那个代价。

两条边界各一个答案：

- `open == count` → 逐点等于 P109 的等分（未折过的画面一像素不动）。
- `open == 0` → **也回等分**：没有人接收那块高度，均摊是唯一不把窗口画成大片空白的答案，
  而且那正是 P110 说的「像现在一样」。另一条路（全折也压成 n 条细线堆在顶上）不难写，画面上
  像坏了。

## 改口的三条旧断言（不是修 bug）

1. P111「折叠一层不移动别人的像素」——**这一轮反转了**，现在是「别人的带反而变高，线段跟着新的
   等分往下走」。反转要在注释里写明是哪一轮翻了哪一条。
2. P111 (5)(6) 按下去用的是前一条算出的 `t1` / `t2`。折一层之后那些坐标落在空白处，**按下去什么
   都不会发生**，而「只有它自己翻了过来」照样变绿（它本来就没翻）。改成每次按之前重新问几何，
   并钉住「它真的翻了面」。
3. P111「箭头折叠前后在同一个位置」——它跟的是**带**，带挪了它就挪。真正不变的是「箭头永远落在
   自己那条带的正中间，而且塞得进去」。

# P114 — 折叠带的厚度 = 一条线的厚度

用户一句话：「我说的是总览界面中，图层的高度，在折叠的情况下，跟一条音符占位符的宽度相等，
或者略宽一点」。

P113 我以为「折叠之后整个图层变成一条线」是「带变薄」，压到 16 设计像素就交了。用户看完说
不是这个意思——**他要的是那条带本身就是一条线的厚度**。P113 的 16 是从「名字要 16 行高」和
「13 px 三角要装得下」推出来的，两个理由都对，都不是「这条带该多厚」。实测带 21 px、线 6.5 px，
三分之二是空气。

## 改法

```
thin = min (7 设计像素, 等分)          // 7 = 线厚上限 5 + 上下各一像素缝
折叠态线厚 = jlimit (1.5, pf (5), 带高 - pf (2))
```

第二条是关键：只改第一条会得到一条 2.7 px 的游丝，因为线厚公式里 `band * 0.30` 在单行时
**就是「带高三成」**。带是因、线是果，只改因，果自己就坏掉。判据用 `rows == nullptr`
（调用方只在折叠时传空表），**不是** `count == 1`——展开的单音高层也是 1 行，那样 133 px 的带
会长出一根填满它的柱子。

缝为什么必须留：两条相邻的折叠带各占满 5 px 会糊成一根 10 px 的粗条，「哪一层折着」就没人
答得出来了。

## 开关：不许消失，但可以换形状

带里放不下名字，也放不下 13 px 的三角。P113 的注释早就写着这个代价（「再薄只能走菜单」），
用户要更薄，所以这一轮必须正面回答。

答案：`getOverviewFoldToggleBounds` 在「三角装不下 + 这条带折着」时返回**整个列宽 × 带高**
（实测 96 × 9）。P111 的规则是「开关长在折叠发生的地方」，不是「开关必须是个三角」。三角照画，
按**短边**量尺（`min (宽, 高) * 0.30`），9 px 带里约 5 px 高——图中放大 6 倍能看见。

**第一版写错了**：判据只写了「折着」。于是 `-overviewfold`（全折）也变——全折回等分，每条带
133 px 高，本来就装得下三角，却被降级成整条带，三角按带高量成跟带一样大。帧比对当场抓到
（那三张帧与 p113 不再相同），加上「三角真的装不下」这个条件之后逐字节回到相同。

- 组仍然铺满整条带（组没有音高），「一个横向跨四层的组算几行」还没有答案。

# P115 — 折叠之后就是窄窄的一条（全折也不例外）

用户一句话：「你还是没有正确理解我的意思，我是想折叠之后就变成窄窄的一条」。

前两轮都在改**厚度**（16 → 7），用户还说不对。这一轮先问「**哪种情况下折叠根本不发生**」，
答案一眼就看出来了：**全部折叠**的时候。P113 把 `open == 0` 留成「回等分」，理由是「没有人接收
那块高度」——而「全都折了」恰恰是三条显眼入口的终点：

- 工具栏第 12 颗 `折叠`（它的语义就是「把剩下的折完」）
- 齿轮菜单第 8 项（管全部）
- **单层工程**（count == 1，一折就是全折）

三条都通向那条分支。用户点折叠 → 按钮亮了、行数变 1 了、**带一寸没动**。

## 改法

```
share  = open > 0 ? (网格高 - thin * folded) / open : thin   // 后者不可达，只为防 0/0
height(i) = 折着 ? thin : share
```

`heightOf` 里原来的 `open > 0 &&` 去掉了：折着的带永远是 `thin`（7 设计像素），从网格**顶边**
依次摞下来，**下面空着**。那片空白就是「这一层收起来了」，与「收起来的轨道摞在顶上」是同一张图。

**为什么空着是对的**：给高度出去是为了别让窗口中间出现空白；但折叠本来就是要留白的。折一下
再把省下的地方塞给别的层，等于让画面替用户决定「你其实想看别的层」。

## 两处改里有一处不可测

第一版只改 `share`，咬测**零红**。原因：`open == 0` 时每条带都折着，`heightOf` 对它们全返回
`thin`，`share` 一次都没被读——那个分支**不可达**。所以代码注释改成「unreachable in effect」，
写明它只为不许 0/0，判据在 `heightOf` 那一处。**一个三元式的一支是死代码，写断言也永远不会红。**

## 三条老断言改口（不是修 bug）

自检立刻红两条（P109 (4)(5)），红法值得记：它们拿**折叠之前**取的 `band0/band1` 去比折叠之后的 y。
以前全折不动带，那句话碰巧成立；这一轮全折让带挪位置、换高度，于是比的是两条不同的带。
同类第三条在 P112 (8)（`块压满条带`），改成**折叠之后重新量**。

教训：断言里同时出现「折叠前的量」与「折叠后的量」时，先问「凭什么它们相等」——理由只能是
「折叠不动带」，而这句话这一轮之后不再成立。

## 自检 1119（条数不变：反转 3、新增 1、删 1）

- (2)(5) 改口径：折叠带 ≤ 7 设计像素；全折的那条改成「一摞窄条 + 剩余为空」。

  剩下的窗口空着（`< grid.bottom - 60 px`）、并且 `< open 带高 * 0.25`（这一句让上一轮的

# P116 — 折叠之后，重叠的音符合成一条

用户一句话：「折叠起来之后，假如有两个音符相重叠，就只显示一个音符从前一个音符的头延续到后一个
音符的尾这样，不要显示中间的重叠，再比如如果有 5 个音符相重叠，就只显示一个音符从第一个音符的头
延续到第五个音符的尾这样」。

P114 把折叠带压到一条线之后，同一层所有音符都落在**同一个 y** 上，我以为这件事就已经成立了。
其实没有：画出来的是**叠在一起的几个矩形**——中间那段 alpha 加了两遍更亮、两头各有一个圆角和
一根亮头，眼睛读到的是「好几段」。用户要的是一个**区间并集**。

## 改法

```
getOverviewMergedRuns (layerIndex) -> vector<OverviewRun { bounds, fade }>
  只对折叠带：收集 [start, start+length]，按起点排序
  吞并：s.from <= to + eps (1e-9) 就算同一段
  每段：overviewFoldedLine (band, x=起点, x=终点)，一个起点头
```

- **只对折叠带生效**。未折叠时音高就是行，重叠是**垂直**关系（「哪两个音撞上了」），合并它是错的。
  这条写在函数第一行，也是自检第 (1) 条（未折叠返回空、两个音各自仍有段）。
- **相接算重叠**：`[0,4)` + `[4,8)` 交集为空，但按耳朵是一个音；按画面中间会冒出一条背景色的缝。
  `eps` 只吸收浮点误差。
- **线厚抽成 `overviewFoldedLine`**：P114 那句（带高减上下各一缝、夹 5 设计 px）原本写在
  `overviewSegmentOf` 里，合并段没有 `NoteEvent` 可传，于是抽出来给两个调用者。**合并段与单音符线
  必须逐点相同**，否则「有几个音重叠」会改变线的粗细。
- **段亮度取最暗的 take**（`takeFadeOf` 取 `jmin`）：吞掉一个静音 take 的段不许看起来像听见的那个。
- 绘制侧：`drawSegment` lambda 一支两用（段 + fade），折叠走 runs、未折叠走逐音符；**一个 run 只有
  一个起点头**，中间那些 onset 正是要消掉的重叠。

## 自检 1119 → 1126（+7）

未折叠不合并 / 两个重叠并成一段（头是前一个的头、尾是后一个的尾）/ 有间隙的不许并（中间空白留着）/
五个重叠并成一段 / 首尾相接算一段 / 合并段与单音符线逐点相同且 fade == 1 / 极短音符合并后仍有最小宽度。

## 咬测五条

| 变异 | 红几条 | 细节 |
|---|---|---|
| M1 不合并（每音符一段） | **5** | `两个重叠` 3 段 / `五个重叠` 5 段 / `首尾相接` 2 段 |
| M2 相接不算（`<`） | **1** | `首尾相接` 变 2 段 |
| M3 合并段自己算几何（30% 带高） | **1** | `288 2.7 / 线 192 6.4` |
| M4 未折叠也合并 | **1** | `未折叠时不合并` 读到 2 段 |
| M5 合并时丢掉最小宽度 | **1** | `最后一段宽 0.5` |

**M3 的第一版零红**，因为它写成「顶边留一缝 + 带高减两缝」，而线高恰好等于「带高减两条缝」——
「居中」与「顶边留一缝」在算术上是**同一个矩形**。等价的变异不是咬测，只能证明同一份公式还有
第二种写法。改成 30% 带高之后才红。

# P117 — 双击一条带 = 打开那一层、去那个时间点

## 改法（一个手势，五步，顺序即规则）

`PianoRollInput.cpp` 的 `handleDoubleClick` 里 P109 那行 `if (overviewMode) return;` 变成
`if (band >= 0) openOverviewBand (band, pos);`（`PianoRollComponent.cpp`）：

   `getOverviewPitchAt` 给音高。**必须在离开模式之前读**：x 轴换模式不变（带与钢琴窗共用时间轴），
   y 轴会变（之后是 128 个琴键，不是这一层的行）。

5. **播放头**：`onLocateRequested (beat)`，与标尺拖动同一个入口。视图不自己写 `playheadBeat`。

新公开查询两个：`getOverviewBandAt (point)`（整个网格宽，答 -1 = 这里没有带：模式外、网格左、

# P118 — 按下红点先问一句：采样还是 MIDI

用户一句话：「录音按钮按下时，先询问是录制采样还是 midi，然后决定录入采样还是 midi」。
P81 起这个按钮只有一个含义，而且**一次按下两边同时 arm**——采集链与事件链一起打开。
于是弹吉他的人碰一下键盘就长出一个「录音 N」音符组，弹键盘的人得到一段没人听过、
却必须先听一遍才敢删的空 WAV。

## 改法

`Audio/Recorder.h` 多了一个值：

```cpp
enum class TakeMode { audio, midi };
struct TakeArming { bool capture, events, monitor; };
constexpr TakeArming takeArmingFor (TakeMode);   // 采样 {1,0,1} / MIDI {0,1,0}
```

`MainComponent`：

- `toggleRecording()` 分两态（`recordPressAction`）：**录中 ⟹ 停（不提问）**，没录 ⟹
  `showRecordMenu()` 弹两项菜单（勾在上次那一项上，取消 = 什么都不录）。
- `startRecording (TakeMode)`：`takeArmingFor` 决定 arm 哪条链、开不开监听；红点保持，
  按钮里改画符号——三条竖线是麦克风、一个音符是键盘。
- `recordNoteAt` / `recordControlAt`：非 MIDI 模式直接 return。**门在采集入口**。
- `finishRecording`：只在 `capture && audioTakeArmed` 时向引擎要样本，收尾清 `audioTakeArmed`。
- `beginTakeForTest (startBeat, mode = midi)`：测试与帧共用同一个入口。

## 一次走错的路（值得记住）

第一版把答案写成 `pianoRoll.flashStatus ("录制采样 · 再按一次红点结束")`。自检 1142 全绿、
帧也出来了，可**帧里的字压在滚动读数上**：`折叠 6.3 / 1录制采样`；MIDI 那张被夹成
`录制 MI..`。原因不是句子长——`drawToolbar` 的 `hintArea` 从第 12 颗工具按钮右边起算，

# P119 — 预备拍永远数不完：一个判据在数学上永远是假的

用户一句话：「在录制midi时，播放头不会往前走，而且按下四个键录进去八个键」。

两个症状看着在两头，其实是同一条：数拍那段 `renderPreRoll` 结束不了，走带就没开始过。

## 病根

```cpp
// 改之前
segment = floor((endBeat - beat) / beatsPerSample);   // 丢掉不足一个采样的余量
...
if (beat >= endBeat - 1.0e-9) { cancelPreRoll(); ... } // 永远假
```

48 kHz / 120 BPM / 480 采样一块：`beat` 停在 **3.999958 / 4**，差 4.17×10⁻⁵ 拍，
比 `1e-9` 大四万多倍 → 此后每块 `segment = 0`、`beat` 不动、`cancelPreRoll()` 永不执行。
P88 规定数拍期间不动播放头，所以用户看到的是"播放头不往前走"。

**八个键是两个 take**：走带不动 ⟹ 每个音符 `beat` 都是同一个 downbeat ⟹ 第二遍四个键
落在与第一遍完全相同的跨度上 ⟹ P95 判它是同一段的第二遍（`active=true`），
第一遍画成 0.45 alpha。两摞 × 四 = 八。

## 改法

1. `PlaybackEngine::renderPreRoll`：`const double samplesLeft = (endBeat - beat) / beatsPerSample;`
   `segment = samplesLeft < numSamples ? floor(samplesLeft) : numSamples;`
   结束判据换成 **`segment < numSamples`**（这一块跑过了数拍的尾巴）——`segment` 已经是
   这一块的结论，不用拿累加值再猜。交接改成显式 `rest = numSamples - segment`，`rest > 0` 才建 buffer。
2. `MainComponent.h`：`static constexpr bool countInApplies (bool transportWasRolling, int countInBeats)`。
3. `startRecording`：`wasRolling` 在 `playTransport()` **之前**读；`countingIn` 同时管
   `startPreRoll` 与 `skipSamples`（两处各算一遍迟早漂）。
4. `recordNoteAt` / `recordControlAt`：模式门之后再问 `isPreRolling()`，是就 return。
   这是 WAV 那半 `samplesToSkip` 的对称；门仍在**采集入口**（P118-C）。

## 自检 1142 → 1148（+6）

- 预备拍照样数得完 ×4：`{480, 960, 128, 1000}` 采样一块，断言 `blocks <= ceil(96000/块)+1`。
- 预备拍只在从静止起步时用（`countInApplies` 三连，细节 `100`）。
- 数拍期间弹的键与拧的旋钮都不进 take；数完之后照收（只剩音高 64 那一个，且音量轨道是平的）。

**两条第一版写错的断言**：
- 数完断言 `positionBeats > 0` → 四条全红；`cancelPreRoll()` 是**本块内**交接，
  这一刻 `positionBeats` 还是 0。改成断言块数。
- CC 门断言"曲线点数为 0" → 红（`曲线点 2`）；`AutomationLane` 默认两个点画平线。
  **"没写入"不等于"没有点"**，改断言"这条 lane 是平的"。

**咬测四条**：还原 `beat >= endBeat - 1e-9` 红 **2**（480 / 960 两条，细节
`4000 块 / 应该有 201 块`）；`countInApplies` 不看走带红 1（`110`）；
音符入口不看预备拍红 1；CC 入口不看预备拍红 1。

**为什么 1142 全绿还是坏的**：夹具块大小是 128，`128 × 750 = 96000` 整除，不卡。
块大小 32..2048 里 **974 个会永久卡死**，480 / 960 停在 3.999958 —— 而 480 正是这台机器
Focusrite 的 buffer。夹具的块大小是坐标，不是背景。

## 真机实测（临时探针，已删）

```
PROBE midi-take trace=0.00/3 0.00/2 0.00/1 0.02/0 1.02/0 2.02/0
PROBE notes=4: [60 2.020..2.620] [61 2.020..2.620] [62 2.020..2.620] [63 2.020..2.620]
```

2 拍/秒 = 120 BPM，数拍那两秒 `positionBeats` 一直是 0（P88 的设计），数完立刻走。
四个键 = 四个音符，都在 2.020..2.620 的真实位置上。

# P120 — 录的时候看得见：录中的音符同步上屏

用户一句话：「在录制midi的时候要同步显示录制的音符」。

P118 之前 take 的两半都只在收尾露面：`commitTake` 落地那一刻组、音符、块才一起出现，
弹琴的人在按停止之前不知道自己弹了什么。P119 那种形状问题（"录进去八个键"）本来
在录的过程中就能看见。

## 改法（一份快照，不是一个副本）

- `Audio/Recorder.h`：`TakeCollector` 加两个只读口 `getRecordedNotes()` /
  `getHeldNotes()`（`HeldNote` 从私有挪到 public）。预览的数据来源只有这一个。
- `MainComponent::publishLiveTakeNotes()`：折成 `PianoRollComponent::LiveNote
  {pitch, velocity, startBeat, endBeat, held}`，在三个时刻重发——键按下、键抬起、
  take 落地（`startRecording` / `beginTakeForTest` 的发布是清空）。**不从 timer 发**。
- `PianoRollComponent`：`setLiveNotes`（列表相等直接返回）+ `getLiveNoteScreenBounds
  (note, atBeat)` + `drawLiveNotes`。按住的音符没有长度，**尾巴就是播放头**；
  `setPlayheadBeat` 里每个 held 音符补一次 `旧矩形 ∪ 新矩形` 的重绘。
- **几何只有一份**：`getNoteBounds` 拆出三参版 `(startBeat, pitch, lengthBeats)`，
  音符与预览都问它——"预览的位置 == 落地的位置"由此成为断言。
- 颜色 `theme::record`，画在 `drawFocusHighlights` 之后：任何东西都不许压住
  一笔正在写的音符。预览不进图层、不进撤销、不进工程文件（v34 不动）。

## 两次走弯的地方（值得记住）

1. **第一版咬测咬不住绘制**：把 `drawLiveNotes (g);` 从 `paint` 里删掉，八条列表断言
   一条不红。第 8 条改成读回卷帘快照：预览格子的中心像素必须从底色变成录音红
   （`r > g+80 && r > b+80`）。列表在手 ≠ 上了屏。
2. **断言取 `front()` 前必须判空**：M2（不发快照）的变异应当让断言红，不是让夹具崩。

## 自检 1148 → 1156（+8）

按下即出现且 held / 尾巴随播放头 / 松键有尾巴而图层没多 / 落地清空且位置逐像素相同 /
录采样无预览 / 数拍期间不上屏 / 新 take 从空开始 / 像素级上屏。

**咬测五条**：尾巴不跟播放头红 1（`5.0 px → 5.0 px`）/ `recordNoteAt` 不发快照红 **7**
（8 条里只剩"录采样"那条活着）/ 新 take 不清空红 1 / 绘制函数没人调红 1 /
画成 accent 红 1。
